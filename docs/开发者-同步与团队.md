# 开发者文档：同步与团队

面向要改这块代码或排查同步问题的人。同步协议的设计（含每条决定的理由与已否决的方案）在
[`docs/superpowers/specs/2026-10-14-sync-team-design.md`](superpowers/specs/2026-10-14-sync-team-design.md)（下文简称 spec）；
共享模型（团队 = 家庭、范围隔离、库存同步）在
[`docs/superpowers/specs/2026-10-24-team-inventory-design.md`](superpowers/specs/2026-10-24-team-inventory-design.md)（下文简称团队 spec），
与本篇冲突时以团队 spec 为准。
部署服务器看 [`SELF-HOSTING.md`](SELF-HOSTING.md)。

## 1. 架构摘要

- **本地 SQLite 是唯一真相源**，服务器不是。App 的每一次读写都只碰本地库，从不「等服务器」。
- **同步链路上服务器只做三件事**：收增量、发增量、存图片；团队（建团 / 邀请码 / 成员）另走 REST（§7）。
  它不参与菜谱的业务逻辑，也不下发任何「权威状态」。
- **服务器是可选的**：没配地址（`hasBaseUrl() === false`）或没登录时，`enqueueSync` 直接返回，
  一条网络请求都不发，App 的所有功能与没有同步功能时完全相同。
- 没有实时推送。客户端在冷启动恢复会话成功后、写操作后（3 秒防抖）、手动点重试时各同步一次。
- 冲突解决是 LWW（后写的赢），没有合并、没有历史、没有冲突提示。

```
App A ──┐                            ┌── App B
 本地库 │  POST /api/v1/sync  ────────►│ 本地库
        │  POST/GET /api/v1/files     │
        └── 走网络才需要服务器 ────────┘
```

## 2. 表结构改动

### 本地 SQLite

只有几处改动，其余七张表和索引一字未动。

| 改动 | 说明 |
|---|---|
| `recipes` 加 `owner_id TEXT` | **NULL = 这台设备上自建、还没认领**。首次登录成功后的第一次同步会把它填成当前账号（认领，spec §9.2）。非 NULL 就是「这条菜谱是谁的」。 |
| 五张业务表加 `scope_id TEXT NOT NULL` | 范围键：`p:<uid>` 个人、`t:<teamId>` 团队、`p:local` 未登录。菜谱、字典三表、库存两表都按它隔离。 |
| `recipes` 加 `owner_nickname TEXT` | 服务端 JOIN `users` 下发的作者昵称，只为离线时在列表里显示「谁加的这道菜」；本机自建、还没推上去的菜谱是 NULL。 |
| 新表 `uploaded_files(name PK, uploaded_at)` | 记录「哪些图片服务器上已经有了」，避免每次同步重复上传（spec §8.2）。 |
| 新表 `teams(id PK, name, role, member_count)` | `GET /teams` 的全量快照（团队列表只走 REST、不进同步载荷）。**不带 `updated_at` / `deleted_at`**：它不是业务实体，是「我加入了谁」的缓存，登录整表替换、登出清空（例外已在 `AGENTS.md` 记录）。 |
| 新表 `cook_records` | 一次制作一条记录（`id`、`scope_id`、`owner_id`、`recipe_id`、`created_at = 制作时间`、`updated_at`、`deleted_at`），另带服务端 JOIN `users` 派生的 `owner_nickname` / `owner_avatar_url`（本机新建时两列是 NULL，显示时回退当前账号）。`recipe_id` 不写 REFERENCES：字典会被物理删、菜谱会软删。 |
| `inventory_usages` 加 `cook_id TEXT` | 把每条扣减归到那条制作记录。老库升级时补成 NULL：存量扣减照旧参与余量计算，但不出现在制作历史里（不回溯，开发阶段数据可清）。 |
| 字典唯一索引带范围 | `UNIQUE(scope_id, name)`（labels 再加 `kind`）：两个家庭各有一个「生抽」互不影响。 |

子表（`recipe_steps` / `recipe_ingredients` / `recipe_labels`）**不加归属列，也不加同步游标**：
它们不是独立业务实体，而是随父菜谱整条替换的快照（spec §7.3），归属由父菜谱的 `owner_id` 决定。

### 服务器 PostgreSQL

`recipes` 有 `owner_id`（NOT NULL，服务端赋值）、`team_id`（NULL = 个人菜谱）、`server_seq`（全局单调游标）；字典三表、库存两表与 `cook_records` 另用 `team_id` / `owner_id` 表达同一个范围；`inventory_usages` 用 `cook_id` 指向那条制作记录；
`ingredients` / `units` / `labels` 三张字典表带 `server_seq`；`files(name PK, owner_id, size, created_at)` 存图片元信息；
`favorites(user_id, recipe_id, created_at)` 与 `follows(follower_id, followee_id, created_at)` 存订阅关系，主键是两列的组合。

四处容易看错的地方：

- 服务器上的 **`recipe_steps` / `recipe_ingredients` / `recipe_labels` 没有 `deleted_at`**。
  服务端只保存「当前有效的子行快照」，软删的子行根本不下发，一个永远为 NULL 的列没有意义。
  这是对 `AGENTS.md`「每张业务表带 `deleted_at`」的**有意例外**，已确认（spec §11.13）；
  本地 SQLite 侧这三张表照旧保留 `deleted_at`。
- 三张子表也**没有 `server_seq`**：它们跟着父菜谱走，不做行级增量（spec §7.3）。
- 字典表上**没有同名唯一约束**。去重靠「同名合并到旧 id」（见 §5），
  撞唯一约束会让整批写入回滚，而合并能自愈。
- `favorites` / `follows` **没有 `id` / `updated_at` / `deleted_at`**：它们不是业务实体，而是「一方的订阅关系」——
  只由本人改写，服务端每次全量下发、客户端整表替换，取消订阅就是删行，软删与 LWW 都用不上（`AGENTS.md` 已记录的例外）。
  索引只有 `idx_favorites_recipe` 一条（按 `user_id` 的查询已被主键覆盖），用于按菜谱反查。

## 3. 协议形状

同步只有两个业务接口：`POST /api/v1/sync` 和 `POST|GET /api/v1/files`（见 §6）。
团队（建团 / 邀请码 / 成员 / 转让 / 解散）走 REST（`/api/v1/teams*`，见 §7），
**不通过同步下发**——同步只搬运菜谱、字典与库存，不搬「我属于哪个团队」。

### 请求

```jsonc
POST /api/v1/sync            // Authorization: Bearer <access token>
{
  "last_server_seq": 128,    // 本地游标；0 = 全量拉
  "local_changes": {
    "ingredients": [ { "id", "scope_id", "name", "created_at", "updated_at", "deleted_at" } ],
    "units":       [ /* 同上 */ ],
    "labels":      [ { "id", "scope_id", "name", "kind", ... } ],   // kind 区分分类与标签
    "recipes": [
      { "id", "scope_id", "name", "cover_path", "category_id", "created_at", "updated_at", "deleted_at",
        "steps":       [ { "id", "sort_order", "text", "image_path" } ],
        "ingredients": [ { "id", "ingredient_id", "amount", "unit_id", "sort_order" } ],
        "label_ids":   [ "<label id>" ] }                 // 子表整条带上，不带各自的时间戳
    ],
    "inventory_batches": [
      { "id", "scope_id", "owner_id", "ingredient_id", "amount", "unit_id",
        "produced_at", "shelf_life_days", "expires_at",
        "created_at", "updated_at", "deleted_at" }
    ],
    "cook_records": [
      { "id", "scope_id", "owner_id", "recipe_id",
        "created_at", "updated_at", "deleted_at" }       // created_at 就是制作时间
    ],
    "inventory_usages": [
      { "id", "scope_id", "owner_id", "cook_id", "recipe_id", "batch_id", "amount",
        "used_at", "updated_at", "deleted_at" }          // used_at 就是发生时间，没有 created_at
    ]
  }
}
```

请求体上限 32MB，但**不含图片字节**。

- **`owner_id` 只在响应里有意义**。请求里带的值一律丢弃：菜谱与批次新增时一律取当前登录用户，
  更新时保留原值；使用记录的 `owner_id` 就是推送者。
- **`scope_id` 是权限边界**（团队 spec §8.2）：`p:<我>` 与 `t:<我加入的团队>` 之外的范围整条跳过，
  不回滚整批。服务端把它翻译成 `team_id` + `owner_id` 再落库。
- 菜谱的范围**在更新时不改**（不做菜谱换本）：库里那条的 `team_id` 与本次推送的范围不一致就整条跳过。
- 推送集合 = 我的范围里的全部字典行（**含软删行**）、`owner_id = 我` 的菜谱与使用记录（**含墓碑**）、
  我的范围里的全部批次。墓碑不推就删不掉，软删字典行不推服务端也删不掉。

### 响应

```jsonc
{
  "server_seq": 431,         // 本次快照的全局游标，客户端存起来下次带回
  "remote_changes": {
    "ingredients": [...], "units": [...], "labels": [...],
    "recipes": [ /* 与请求同形状，外加 "owner_id"、"owner_nickname" 与 "owner_avatar_url"（作者没设头像时为 null） */ ],
    "cook_records": [ /* 外加服务端派生的 "owner_nickname" 与 "owner_avatar_url" */ ],
    "inventory_batches": [...], "inventory_usages": [...],
    "files":   [ { "name": "3f2a....jpg", "size": 184320 } ]
  }
}
```

- `files` **只列本次 `remote_changes.recipes` 引用到的图片**，客户端对本地没有的逐个下载。
- 可见范围过滤在**服务端 SQL 里**就做了，不是发完再让客户端筛：
  可见 ⇔ `team_id IS NULL AND owner_id = 我` **或** `team_id 在我加入且未解散的团队里`（`visibleRecipesSQL`）。
  字典三表与库存两张表用同一条范围条件（`visibleRecipesSQL` 也被 `FileService.CanRead` 共用，两条通道不会漂移）。
- `owner_nickname` / `owner_avatar_url` 由服务端 `LEFT JOIN users` 取 `nickname` / `avatar_url`：客户端的列表要能离线显示「谁加的这道菜」。
- 制作记录与使用记录一起下发：`queryUsages` 的 SELECT 带 `cook_id`，否则别的设备详情页看不到明细；
  服务端合并时**记录在前、使用记录在后**（使用记录指向它），且 `insertUsage` 不校验 `cook_id` 是否存在 ——
  记录被范围校验跳过时也要保住这条扣减，丢了它会永久对不上库存。
- `backfillInventoryDicts`：批次的 `ingredient_id` / `unit_id` 可能指向本次没下发的字典行（`server_seq` 早于游标），同样按 id 反查补齐。
- `backfillReferenced`：增量里的菜谱可能引用三天前建的食材（它的 `server_seq` 早于游标、本次没下发），
  服务端按 id 反查补齐父行，否则客户端会引到不存在的行。子表随菜谱整条走，所以只需要补字典这一层。

## 4. LWW 与游标

### 时间基础

- 本地写库统一 ISO 8601 UTC 字符串。比较前一律经 `toIsoTimestamp()` 归一化，
  用 `compareTimestamp()` 按 epoch 毫秒比。
- **必须归一化的原因**：SQLite 的 `datetime('now')` 产出 `"YYYY-MM-DD HH:MM:SS"`，
  Go 的 `time.Time` 解析不了这个格式，会让整个 `/sync` 请求体被 400 拒掉；
  直接用字典序比字符串还会把 `" "` 和 `"T"` 的大小关系判错。
- **LWW 比较用的是记录里的 `updated_at`，不是服务器的 `now()`**。
  服务端只在「新记录的 `updated_at` 严格大于库里的」时才写入。

### 游标

- 游标是一个**全局单调**的 `server_seq` 数字，不是按表分的。
- 拉取在单个 `REPEATABLE READ` 只读事务里，先读本次增量，再取快照内的 `MAX(server_seq)` 当新游标。
- 服务端写事务开始时先取 `pg_advisory_xact_lock`，把所有同步写事务串行化，
  保证 `server_seq` 的赋值顺序等于提交顺序（并发交错提交会出现「低 seq 晚提交」被已推进的游标永久跳过）。
- 新增一个团队后，那个团队里那些 `server_seq` 早于游标的行靠增量永远拉不下来，所以建团 / 入团后要清游标（§7）。
  所以服务端在写 `favorites` 的**同一个事务**里把该菜谱的 `server_seq` 推进到最新（见 §7）。

### 墓碑

- 删除 = 写 `deleted_at`（软删）。列表查询一律 `WHERE deleted_at IS NULL`，行本身留着。
- 远端墓碑到了就跟着写 `deleted_at`，本地父行保留；子行随父行整组替换，墓碑时即删空（不落软删行）。
- 别人删掉的、我原本看得到的菜谱，墓碑会下发到我这儿，我本地跟着消失——否则它会在我这儿永远复活。

### 服务器换世代

服务器库被重建或恢复旧备份后，`MAX(server_seq)` 会低于客户端手里的游标，客户端会永远拉不到新数据。
协议里**没有**世代字段；服务端在同一个快照里比「客户端游标 vs `MAX(server_seq)`」，
发现回退就按 `sinceSeq = 0` 重读一次全量（LWW 幂等），并把返回的 `server_seq` 退回当前世代的最大值。
账号行不在新库里时客户端会从 `/me` 拿到 401，重新登录即可。

## 5. 字典同名合并

字典（`ingredients` / `units` / `labels`）在服务器上全局共享一份，没有归属列。

- **合并键**：`ingredients` / `units` 按 `(name)`；`labels` 按 `(name, kind)`——与本地唯一索引
  `idx_labels_name_kind` 一致。分类和标签**不能**并成一行：同名不同 `kind` 是两种东西，
  而 `recipes.category_id` 与 `recipe_labels.label_id` 都指向这张表，跨 kind 合并会把一条菜谱的分类变成标签。
- **服务端**：推送 `id = X` 的行时，若 X 不存在但同键的行已存在（`id = Y`，**含软删行**）→ 内容合并进 Y、丢弃 X、返回 Y。
- **软删行也必须参与合并**：本地清库重绑会重新生成 UUID，而软删行仍然占着「同名」这个坑；
  漏判就会写出两条同名数据，两个客户端从此各看各的。
- **客户端做同一件事的镜像**（`applyRemoteChanges`）：收到 id = Y 的字典行、而本地已有同键的 X 时，
  把引用改指 Y（`recipe_ingredients.ingredient_id` / `unit_id`、`recipes.category_id`、`recipe_labels.label_id`，
  以及**同一批 `remote_changes.recipes` 子数组里的引用**）→ 删掉 X → 插入 Y。
  协议里**没有 `id_remap` 字段**：服务端返回的增量天然带着 Y（Y 的 `server_seq` 被推进了）。
- 本地插新字典行的顺序被外键钉死：先软删老行释放唯一键 → 插新行 → 改指引用 → 硬删老行。
  查同键行时优先取**活行**（`ORDER BY (deleted_at IS NULL) DESC`）——先取到软删行、只软删它，
  并不会释放 `name` 上的局部唯一索引，随后的 INSERT 会撞活行，同步就此永远卡死。
- 软删的字典行**不阻止**已引用它的菜谱正常显示（详情页 JOIN 不筛 `deleted_at`），只是不再出现在选择列表里。同名再建一次等于复活。

## 6. 图片通道

图片不走 `/sync`，走独立的两个接口。

```
POST /api/v1/files?name=<裸文件名>   body = 裸二进制  → 200 { "name", "size" }
GET  /api/v1/files/{name}                           → 200 二进制 / 404
```

- **按文件名做键**，不是内容哈希。文件名是客户端生成的 `<uuid>.jpg`，全局唯一；服务端只校验形状，
  带路径分隔符的值一律拒绝。同名已存在直接 200，不覆盖。单文件 ≤ 5MB，且必须是 JPEG（看前三个字节）。
  （不做内容哈希的理由：要客户端把整个文件读一遍算 sha256，换来的只是「同一张图重复上传时省磁盘」，
  自托管规模下几乎不发生。）
- **上传前先查 `uploaded_files` 去重**，只传本地没有记录的。查本地表而不是问服务器，省一次往返；
  代价是本机清库重装后会把图重传一遍，视为可接受的浪费。
- **任何一张图传不上去，这批菜谱就整批不推**（字典照推）。宁可晚一个周期，
  也不要让服务器上出现「菜谱已到、封面还没有」的持久状态——对方会看到一张永远空着的封面。
  失败的那张不写 `uploaded_files`，下次同步自然重试；同批里已经传上去的照常记账。
- **下载失败不阻塞菜谱落地**。菜谱先落库、图后补，UI 上就是暂时没封面。串行下载，先写 `.tmp` 再改名，
  正式名要么不存在、要么就是完整文件。200 但对空 body 也当失败处理（否则空文件一旦占了正式名就永不重下）。
- **读权限由「引用它的菜谱」反查**，不是看文件自己的归属：
  可见 ⇔ 存在一条菜谱引用了它（`cover_path` 或某条步骤的 `image_path` 等于这个文件名），
  且那条菜谱要么是**我的**（含软删的），要么是**公开且未删除的**（`FileService.CanRead`）。
  这样可见性永远跟着使用它的菜谱走，不会出现「先上传成私人的、后来公开 → 别人 403、封面永远空白」。
  **副作用（已知限制）：孤儿图片谁都读不了**——菜谱被删或改了封面之后，那张图还在磁盘上占空间但取不回来。
  本轮不做垃圾回收，也不做配额。

## 7. 团队与范围

共享单位是**团队（= 家庭）**：菜谱、库存、字典都归一个范围，一个人可以属于多个团队并在界面上切换。
社区（公开菜谱 / 收藏 / 关注 / 用户页）已整块删除。

### 范围（当前团队）

- 一个全局状态 `currentTeamId`（`null` = 「我的菜谱」），派生出范围键 `scope_id`：

| 状态 | 范围键 | 显示 |
|---|---|---|
| 有当前团队 | `t:<teamId>` | 该团队的菜谱 / 库存 / 字典 |
| 已登录、无当前团队 | `p:<uid>` | 我的个人菜谱 / 库存 / 字典 |
| 未登录 | `p:local` | 本机未认领的数据 |

- 持久化在 `localStorage["current_team:<uid>"]`，按账号隔离；冷启动恢复上次选中的范围，
  那个团队已不在缓存里就回落「我的菜谱」。
- **创建 / 加入团队后自动切到那个团队**；退出 / 被移除 / 解散时若正在看它 → 回落「我的菜谱」。
- 切范围时刷新所有受范围影响的 store（菜谱、库存、字典），不重新拉网络。

### REST 接口

团队列表只走 REST，不进同步载荷（团队是「我的身份」，不是内容）。

| 接口 | 说明 |
|---|---|
| `GET /api/v1/teams` | 我加入的、未解散的团队 + 成员数 + 我的角色 |
| `POST /api/v1/teams` | 建团（建者即 owner） |
| `POST /api/v1/teams/join` | 6 位邀请码入组（**按 IP 限流 10/min**：码只有 100 万种，不限流就是可暴力枚举的入组口） |
| `PUT /api/v1/teams/{id}` | 改名（owner） |
| `POST /api/v1/teams/{id}/invite` | 生成 6 位邀请码（owner，Redis 存 24h） |
| `GET /api/v1/teams/{id}/members` | 成员列表（成员） |
| `DELETE /api/v1/teams/{id}/members/{userId}` | 移除成员（owner，不能移除自己） |
| `DELETE /api/v1/teams/{id}/members/me` | 退出（member；owner 要先转让或解散） |
| `PUT /api/v1/teams/{id}/owner` | 转让 owner（owner，目标必须是本团队成员） |
| `DELETE /api/v1/teams/{id}` | 解散（owner，软删 `teams` 行） |

- 邀请码存 Redis：`invite:<6位>` → `teamID:creatorID`，TTL 24h；**入组成功后才删码**（失败可重试）。
- 角色只有 `owner` / `member`，一个团队**恰好一个 owner**。
- 解散只软删 `teams` 行：`team_members` 与团队的菜谱 / 库存 / 字典都不删（成员查不到即可）。
- 越权一律 403 / 404。

### 建团 / 入团后清游标

客户端只有一个全局游标。新加入的团队里，那些 `server_seq` 早于游标的行否则永远拉不下来
（旧团队设计踩过的坑）。所以 `create` / `join` 成功后：`load()` → `switchTo(newId)` →
`clearSyncCursorFor(uid)` → `requestSyncNow()`，等于把该范围当「从零开始」重拉一遍。

### 图片读权限

`FileService.CanRead` 的可见范围 = 引用它的菜谱在我可见范围内（个人 ∪ 我的团队），
与同步增量共用同一条 `visibleRecipesSQL`。团队解散后成员就读不到团队菜谱的图了。

## 8. 客户端行为要点

| 点 | 规则 |
|---|---|
| 单库 + 范围列 | 不按账号 / 团队分库，一个 SQLite 文件里住着多个范围的数据，**每个查询都带 `scope_id = 当前范围`**。登出后未登录界面只看 `p:local`（认领后为空 ⇒ 空态），登录回来数据都在。 |
| 可改范围 | 一律 `owner_id = 我`（未登录时是无主行）。**能看的比能改的宽**：别人的菜谱只读。否则登出期间改了别人的公开菜谱，本地 `updated_at` 更新、推上去被服务端跳过，这条改动永远赢着，两边永久分叉。 |
| 编辑入口 | 非作者在详情页**不渲染**编辑/删除按钮（服务端校验只是第二道锁，不能当唯一防线）。 |
| 推送集合 | `owner_id = 我` 的全部菜谱 + 全部字典行，**不是只推队列里那几个**。队列会被清、登出期间录的菜不进队、上次推到一半崩了——只有全扫能补上。LWW 幂等，重复推没有副作用。 |
| 会话变在线 | 登录成功 / 注册成功 / 冷启动恢复会话成功 → 记下本机账号（`local_accounts`）→ 认领无主菜谱 → 一次全扫推送与拉取（`triggerFullPushAndSync`）。 |
| 触发 | 写操作后 `enqueueSync`，3 秒防抖；失败按 5s → 10s → 20s → 40s → 60s 退避（指数翻倍，上限 60s）；`performSync` 带互斥 + 补跑。 |
| 队列与游标 | **都按 uid 隔离**（`pending_sync:<uid>` / `last_server_seq:<uid>`）并落盘。单例队列会让 A 的改串到 B 账号；不落盘则 3 秒定时器没烧完就退出 App 会丢改动。 |
| 登出 | 只停定时器，**保留**各 uid 的积压队列，下次同一账号登录继续推。 |

## 9. 常见问题排查

**1）同步一直失败，「我的」页显示「上次同步没成功」**

先看「我的」页那条红字，再按顺序查：

```bash
docker compose ps                                   # api 是不是 Up
docker compose logs api | tail -50                  # 服务端错误
curl -s <你填的地址>/api/v1/healthz                  # 客户端探活用的就是它
```

- `healthz` 通、App 还是报错 → 看路径：地址栏里**不要带 `/api/v1`**，填 `http://192.168.1.10:8080` 这种。
- 地址对但一直失败 → 401 通常是 token 过期且 refresh 也失败，退出登录重新登录一次。
- 服务端日志里是 `password authentication failed` → 容器的 `POSTGRES_PASSWORD` 与
  既有 `pgdata` 卷创建时的不一致（该变量**只在首次初始化数据库时生效**），改成当时的那个值即可。
- 网络本身不通（另一台设备连不上这台服务器）→ 检查服务器防火墙放行 8080。

**2）看不到队友的菜谱 / 库存**

- 先确认在同一个范围里：页头切换器上是不是同一个团队（而不是「我的菜谱」）。
- 确认对方真的同步成功了（让他手动点一次重试）；同步失败时界面会显示失败态。
- 冷启动后切不上团队 → `GET /teams` 没拿到（401 说明登录失效），重新登录一次。
- 入团后看不到入团前的存量 → 建团 / 入团要清游标（§7）；清完还不行就退出重进一次。

**3）封面是空白的**

- 服务端那批菜谱根本没有图 → 上传至少有一张失败，客户端会把**整批菜谱**都扣下（§6），
  所以对方那边「有菜谱但没封面」意味着你本机下次同步还会重试上传。检查本机图片文件是否还在
  （`$APPDATA/images/<name>`）、是否超过 5MB。
- 图曾经能看、后来变白 → 服务端的图被清理或卷被重建；`GET /files/{name}` 现在是 404。
  **客户端对 404 不重试**：这条菜谱已经落库，只有菜谱本身再次变化（`updated_at` 更新）时
  才会重新带出这条引用、重新排队下载。
- 压根没同步过图（比如只在桌面端 dev 里跑）→ 确认这台设备的 `$APPDATA/images/` 目录可写。

**4）改不了别人的菜谱**

设计如此，不是 bug。规则是「只有录的人能改能删」：非作者在详情页看不到编辑和删除按钮
（不是灰掉，是不渲染），服务端收到越权写入也会静默跳过。想改就自己新建一条。

**5）服务器库被重建，或恢复了一份旧备份**

- 服务端有世代护栏：`MAX(server_seq)` 低于客户端游标时，客户端自动按全量重拉一次，游标退回当前世代，不需要你做什么。
- 但**账号行若不在新库里**，`/me` 会 401、刷新令牌也失败 → 在 App 里**重新登录**（或重新注册），新账号从零开始同步；
  本机的菜谱会在认领后重新推上去。
- 图片是另一个卷，`docker compose down -v` 会连图一起删掉；只 `down` 不会。恢复图见 `SELF-HOSTING.md` 的备份一节。

**6）换手机后登录，本机原有的菜谱没上来**

只有当本地那条菜谱的 `owner_id` 是 NULL（本机自建、从未认领）时才会上推。
已被别的账号认领过的菜谱（例如同一台设备换人登录过）不会推给新账号。
另外确认这台设备的 `pending_sync:<uid>` 没被外部清掉——清掉也没关系，登录/恢复会话时的那次全扫推送会兜住。

## 10. 已知限制

按重要程度排，**都是刻意不做、不是漏做**：

1. **时钟偏差**。LWW 用的是记录里的 `updated_at`，客户端的时间快就会一直赢。
   更糟的是：**LWW 输掉的那次修改是无声丢弃的**——不提示、不保留历史、没有回收站。
   冲突只可能发生在「同一个人的两台设备」上（只有作者能改），所以没有做冲突解决。
2. **图片不做垃圾回收，也没有配额**。删菜谱不删图，换封面也不删旧图；孤儿图谁都读不了但占着磁盘。
   磁盘满了要自己清 `files` 卷。将来加 GC 时的依据是「还有没有菜谱引用它」（含软删菜谱）。
3. **团队只有建团、邀请码入组、改名、成员管理四件事**：没有评论、点赞、通知、动态流，也没有跨团队的公开分享。
4. **菜谱只有「个人 / 团队」两种范围**：团队菜谱全队可见，但**只有创建者能改**（整条替换的合并以「只有作者能改」为前提）。
   没有「单条菜谱只分享给某个人」的中间档，也没有把菜谱在个人与团队之间搬家的功能（不做菜谱换本）。
5. **退出 / 被移除团队后，本地的团队数据不删**：只是不在界面上显示、也不再被推送（不在我的范围里）。
   重新加入就又能看到；真要清理由用户自己决定。
6. **子表整条替换**：改一次菜谱（哪怕只改一个字）会重传它的全部步骤与用料。家用规模的数据量下可忽略。
7. **并发扣减不解决**：两个人几乎同时点「确认制作」会把同一批次扣两次，余量按 0 兜底显示（`已用完`），
   账实偏差由用户自己删批次 / 再录一批修正。
   代码里留了 `shortcut:` 注释：将来允许协作编辑同一条菜谱时，必须回到行级 LWW（spec §7.3）。
8. **没有实时推送**，最长要等 3 秒防抖或下一次冷启动。
8. 字典是**全服务器共享**的，不分用户：同一台服务器上任何登录用户都能改别人建的食材名。
   自托管假设是「服务器属可信域」。升级路径是给三张字典表加归属列并按用户过滤。

### 桌面端两个实例（两个不同的 `$APPDATA`，或一台真机 + 桌面端）

服务器地址填 `http://localhost:8080`（不带 `/api/v1`）。

| # | 操作 | 要看到什么 |
|---|---|---|
| 1 | A 注册 → 录一条带封面的私人菜谱 | 「我的」页显示上次同步时间；服务端库里有这条菜谱 |
| 2 | A 建「自己家」→ 生成邀请码 → B 加入 | B 的切换器里出现「自己家」 |
| 3 | A 在「自己家」录一道菜、录一批五花肉 | B 切到「自己家」都看得到；B 切回「我的菜谱」看不到 |
| 4 | B 对这道菜点「确认制作」 | A 下次同步后余量变少 |
| 5 | A 在「爸妈家」录食材「生抽」 | 切到「自己家」，食材选择里没有它；两边各有一个「生抽」互不合并 |
| 6 | B 试图改 A 创建的菜谱 | 没有编辑按钮；直接进编辑路由也被拦 |
| 7 | A 先录 5 道 → B 才入团 | B 入团后 5 道都在（清游标的全量重拉） |
| 8 | 游客录一道菜 + 一批库存 → 登录 → 登出 | 登录后两者都在并开始同步；登出界面空态；再登录都在 |
| 9 | 同一台手机 A 登出、B 登录 | B 看不到 A 的任何菜谱 / 库存 / 食材 |
| 8 | B 断网 → 录一条私人菜谱 + 改字典 → 恢复网络 → 同步 | A 看不到 B 的私人菜谱；B 的改动同步上去了 |
| 9 | A 的两台设备改同一条菜谱 | 同步后两边都是较新的那份（LWW） |
