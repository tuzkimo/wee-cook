# 开发者文档：同步与团队

面向要改这块代码或排查同步问题的人。完整设计（含每条决定的理由与已否决的方案）在
[`docs/superpowers/specs/2026-10-14-sync-team-design.md`](superpowers/specs/2026-10-14-sync-team-design.md)（下文简称 spec）。
部署服务器看 [`SELF-HOSTING.md`](SELF-HOSTING.md)。

## 1. 架构摘要

- **本地 SQLite 是唯一真相源**，服务器不是。App 的每一次读写都只碰本地库，从不「等服务器」。
- **服务器只做三件事**：收增量、发增量、存图片。它不参与业务逻辑，也不下发任何「权威状态」。
- **服务器是可选的**：没配地址（`hasBaseUrl() === false`）或没登录时，`enqueueSync` 直接返回，
  一条网络请求都不发，App 的所有功能与没有同步功能时完全相同。
- 没有实时推送。客户端在冷启动恢复会话成功后、写操作后（3 秒防抖）、手动点重试时各同步一次。
- 冲突解决是 LWW（后写的赢），没有合并、没有历史、没有冲突提示。

```
App A ──┐                            ┌── App B
 本地库 │  POST /api/v1/sync  ────────►│ 本地库
        │  POST/GET /api/v1/files     │
        └── 走网络才需要服务器 ────────┘
```

## 2. 表结构改动

### 本地 SQLite

只有两处改动，其余七张表和索引一字未动。

| 改动 | 说明 |
|---|---|
| `recipes` 加 `owner_id TEXT` | **NULL = 这台设备上自建、还没认领**。首次登录成功后的第一次同步会把它填成当前账号（认领，spec §9.2）。非 NULL 就是「这条菜谱是谁的」。 |
| `recipes` 加 `team_id TEXT` | **NULL = 私人菜谱**（只有 `owner_id` 本人、本人所有设备可见）；非 NULL 就是某个家庭 id。 |
| 新表 `uploaded_files(name PK, uploaded_at)` | 记录「哪些图片服务器上已经有了」，避免每次同步重复上传（spec §8.2）。 |

子表（`recipe_steps` / `recipe_ingredients` / `recipe_labels`）**不加归属列，也不加同步游标**：
它们不是独立业务实体，而是随父菜谱整条替换的快照（spec §7.3），归属由父菜谱的 `owner_id` / `team_id` 决定。

### 服务器 PostgreSQL

`recipes` 多出 `owner_id`（NOT NULL，服务端赋值）、`team_id`（NULL = 私人）、`server_seq`（全局单调游标）；
`ingredients` / `units` / `labels` 三张字典表带 `server_seq`；`files(name PK, owner_id, size, created_at)` 存图片元信息。

三处容易看错的地方：

- 服务器上的 **`recipe_steps` / `recipe_ingredients` / `recipe_labels` 没有 `deleted_at`**。
  服务端只保存「当前有效的子行快照」，软删的子行根本不下发，一个永远为 NULL 的列没有意义。
  这是对 `AGENTS.md`「每张业务表带 `deleted_at`」的**有意例外**，已确认（spec §11.13）；
  本地 SQLite 侧这三张表照旧保留 `deleted_at`。
- 三张子表也**没有 `server_seq`**：它们跟着父菜谱走，不做行级增量（spec §7.3）。
- 字典表上**没有同名唯一约束**。去重靠「同名合并到旧 id」（见 §5），
  撞唯一约束会让整批写入回滚，而合并能自愈。

## 3. 协议形状

只有两个业务接口：`POST /api/v1/sync` 和 `POST|GET /api/v1/files`（见 §6）。
团队走 REST（`GET/POST /api/v1/teams`、`/teams/{id}/invite`、`/teams/join`、`/teams/{id}/members`），
**不通过同步下发**——服务端不把 team 当成一行数据传下来。

### 请求

```jsonc
POST /api/v1/sync            // Authorization: Bearer <access token>
{
  "last_server_seq": 128,    // 本地游标；0 = 全量拉
  "local_changes": {
    "ingredients": [ { "id", "name", "created_at", "updated_at", "deleted_at" } ],
    "units":       [ /* 同上 */ ],
    "labels":      [ { "id", "name", "kind", ... } ],   // kind 区分分类与标签
    "recipes": [
      { "id", "name", "cover_path", "category_id", "created_at", "updated_at", "deleted_at",
        "team_id",
        "steps":       [ { "id", "sort_order", "text", "image_path" } ],
        "ingredients": [ { "id", "ingredient_id", "amount", "unit_id", "sort_order" } ],
        "label_ids":   [ "<label id>" ] }                 // 子表整条带上，不带各自的时间戳
    ]
  }
}
```

请求体上限 32MB，但**不含图片字节**。

- **`owner_id` 只在响应里有意义**。请求里带的值一律丢弃，服务端一律赋当前登录用户。
- **`team_id` 必须是当前用户所在的家庭**，否则整条菜谱跳过（不报错、静默跳过）。
- 推送集合 = `owner_id = 我` 的全部菜谱（**含墓碑**）+ 全部字典行（**含软删行**）。
  墓碑不推就删不掉，软删字典行不推服务端也删不掉。

### 响应

```jsonc
{
  "server_seq": 431,         // 本次快照的全局游标，客户端存起来下次带回
  "remote_changes": {
    "ingredients": [...], "units": [...], "labels": [...],
    "recipes": [ /* 与请求同形状，外加 "owner_id" */ ],
    "files":   [ { "name": "3f2a....jpg", "size": 184320 } ]
  }
}
```

- `files` **只列本次 `remote_changes.recipes` 引用到的图片**，客户端对本地没有的逐个下载。
- 可见范围过滤在**服务端 SQL 里**就做了，不是发完再让客户端筛：
  私人菜谱只发给 `owner_id` 本人，团队菜谱只发给该家庭成员；字典三张表无过滤（全服务器共享一份）。
- `backfillReferenced`：增量里的菜谱可能引用三天前建的食材（它的 `server_seq` 早于游标、本次没下发），
  服务端按 id 反查补齐父行，否则客户端会引到不存在的行。子表随菜谱整条走，所以只需要补字典这一层。

## 4. LWW 与游标

### 时间基础

- 本地写库统一 ISO 8601 UTC 字符串。比较前一律经 `toIsoTimestamp()` 归一化，
  用 `compareTimestamp()` 按 epoch 毫秒比。
- **必须归一化的原因**：SQLite 的 `datetime('now')` 产出 `"YYYY-MM-DD HH:MM:SS"`，
  Go 的 `time.Time` 解析不了这个格式，会让整个 `/sync` 请求体被 400 拒掉；
  直接用字典序比字符串还会把 `" "` 和 `"T"` 的大小关系判错。
- **LWW 比较用的是记录里的 `updated_at`，不是服务器的 `now()`**。
  服务端只在「新记录的 `updated_at` 严格大于库里的」时才写入。

### 游标

- 游标是一个**全局单调**的 `server_seq` 数字，不是按表、也不是按家庭分的。
- 拉取在单个 `REPEATABLE READ` 只读事务里，先读本次增量，再取快照内的 `MAX(server_seq)` 当新游标。
- 服务端写事务开始时先取 `pg_advisory_xact_lock`，把所有同步写事务串行化，
  保证 `server_seq` 的赋值顺序等于提交顺序（并发交错提交会出现「低 seq 晚提交」被已推进的游标永久跳过）。
- **加入/创建家庭成功后必须把当前 uid 的游标清 0**（`clearCursor`），下一次同步就是一次全量拉取。
  **为什么必须清**：游标是跨家庭共享的一个数字。B 在 A 录了 50 道团队菜谱之后才用邀请码加入，
  那 50 行的 `server_seq` 早已小于 B 的游标，按「`server_seq > 游标`」永远拉不到，B 看到的家庭是空的，
  而且**不报任何错**。`POST /teams` 与 `POST /teams/join` 成功后都会清（少清一个就漏）。
  不做「按家庭分游标」，那是为省一次全量拉取而引入一套并行的游标体系，家庭规模下不值。

### 墓碑

- 删除 = 写 `deleted_at`（软删）。列表查询一律 `WHERE deleted_at IS NULL`，行本身留着。
- 远端墓碑到了就跟着写 `deleted_at`，本地父行保留；子行随父行整组替换，墓碑时即删空（不落软删行）。
- 别人删掉的、我原本看得到的菜谱，墓碑会下发到我这儿，我本地跟着消失——否则它会在我这儿永远复活。

### 服务器换世代

服务器库被重建或恢复旧备份后，`MAX(server_seq)` 会低于客户端手里的游标，客户端会永远拉不到新数据。
协议里**没有**世代字段；服务端在同一个快照里比「客户端游标 vs `MAX(server_seq)`」，
发现回退就按 `sinceSeq = 0` 重读一次全量（LWW 幂等），并把返回的 `server_seq` 退回当前世代的最大值。
账号行不在新库里时客户端会从 `/me` 拿到 401，重新登录即可。

## 5. 字典同名合并

字典（`ingredients` / `units` / `labels`）在服务器上全局共享一份，没有归属列。

- **合并键**：`ingredients` / `units` 按 `(name)`；`labels` 按 `(name, kind)`——与本地唯一索引
  `idx_labels_name_kind` 一致。分类和标签**不能**并成一行：同名不同 `kind` 是两种东西，
  而 `recipes.category_id` 与 `recipe_labels.label_id` 都指向这张表，跨 kind 合并会把一条菜谱的分类变成标签。
- **服务端**：推送 `id = X` 的行时，若 X 不存在但同键的行已存在（`id = Y`，**含软删行**）→ 内容合并进 Y、丢弃 X、返回 Y。
- **软删行也必须参与合并**：本地清库重绑会重新生成 UUID，而软删行仍然占着「同名」这个坑；
  漏判就会写出两条同名数据，两个客户端从此各看各的。
- **客户端做同一件事的镜像**（`applyRemoteChanges`）：收到 id = Y 的字典行、而本地已有同键的 X 时，
  把引用改指 Y（`recipe_ingredients.ingredient_id` / `unit_id`、`recipes.category_id`、`recipe_labels.label_id`，
  以及**同一批 `remote_changes.recipes` 子数组里的引用**）→ 删掉 X → 插入 Y。
  协议里**没有 `id_remap` 字段**：服务端返回的增量天然带着 Y（Y 的 `server_seq` 被推进了）。
- 本地插新字典行的顺序被外键钉死：先软删老行释放唯一键 → 插新行 → 改指引用 → 硬删老行。
  查同键行时优先取**活行**（`ORDER BY (deleted_at IS NULL) DESC`）——先取到软删行、只软删它，
  并不会释放 `name` 上的局部唯一索引，随后的 INSERT 会撞活行，同步就此永远卡死。
- 软删的字典行**不阻止**已引用它的菜谱正常显示（详情页 JOIN 不筛 `deleted_at`），只是不再出现在选择列表里。同名再建一次等于复活。

## 6. 图片通道

图片不走 `/sync`，走独立的两个接口。

```
POST /api/v1/files?name=<裸文件名>   body = 裸二进制  → 200 { "name", "size" }
GET  /api/v1/files/{name}                           → 200 二进制 / 404
```

- **按文件名做键**，不是内容哈希。文件名是客户端生成的 `<uuid>.jpg`，全局唯一；服务端只校验形状，
  带路径分隔符的值一律拒绝。同名已存在直接 200，不覆盖。单文件 ≤ 5MB，且必须是 JPEG（看前三个字节）。
  （不做内容哈希的理由：要客户端把整个文件读一遍算 sha256，换来的只是「同一张图重复上传时省磁盘」，
  家庭场景下几乎不发生。）
- **上传前先查 `uploaded_files` 去重**，只传本地没有记录的。查本地表而不是问服务器，省一次往返；
  代价是本机清库重装后会把图重传一遍，视为可接受的浪费。
- **任何一张图传不上去，这批菜谱就整批不推**（字典照推）。宁可晚一个周期，
  也不要让服务器上出现「菜谱已到、封面还没有」的持久状态——用户会在家人手机上看到一个永远空着的封面。
  失败的那张不写 `uploaded_files`，下次同步自然重试；同批里已经传上去的照常记账。
- **下载失败不阻塞菜谱落地**。菜谱先落库、图后补，UI 上就是暂时没封面。串行下载，先写 `.tmp` 再改名，
  正式名要么不存在、要么就是完整文件。200 但对空 body 也当失败处理（否则空文件一旦占了正式名就永不重下）。
- **读权限由「引用它的菜谱」反查**，不是看文件自己的归属：
  可见 ⇔ 存在一条**我可见的**菜谱（含软删菜谱）的 `cover_path` 或某条步骤的 `image_path` 等于这个文件名。
  这样可见性永远跟着使用它的菜谱走，不会出现「先上传成私人的、后来被团队菜谱引用 → 队友 403、封面永远空白」。
  **副作用（已知限制）：孤儿图片谁都读不了**——菜谱被删或改了封面之后，那张图还在磁盘上占空间但取不回来。
  本轮不做垃圾回收，也不做配额。

## 7. 客户端行为要点

| 点 | 规则 |
|---|---|
| 单库 + 过滤 | 不按用户分库，一个 SQLite 文件里可能同时住着几个人的数据。未登录**不过滤**（认领后 `owner_id` 已填成某个账号，过滤会让人以为数据丢了），已登录显示 `owner_id = 我` 的私人菜谱 + 我在的家庭的全部菜谱。 |
| 可改范围 | 一律 `owner_id = 我`（未登录时是无主行）。**未登录时能看的比能改的宽**：别人的菜谱只读。否则登出期间改了家人的团队菜谱，本地 `updated_at` 更新、推上去被服务端跳过，这条改动永远赢着，两边永久分叉。 |
| 编辑入口 | 非作者在详情页**不渲染**编辑/删除按钮（服务端校验只是第二道锁，不能当唯一防线）。 |
| 推送集合 | `owner_id = 我` 的全部菜谱 + 全部字典行，**不是只推队列里那几个**。队列会被清、登出期间录的菜不进队、上次推到一半崩了——只有全扫能补上。LWW 幂等，重复推没有副作用。 |
| 会话变在线 | 登录成功 / 注册成功 / 冷启动恢复会话成功 → 认领无主菜谱 → 一次全扫推送与拉取 → 刷新团队列表（`triggerFullPushAndSync`）。 |
| 触发 | 写操作后 `enqueueSync`，3 秒防抖；失败按 5s → 10s → 20s → 40s → 60s 退避（指数翻倍，上限 60s）；`performSync` 带互斥 + 补跑。 |
| 队列与游标 | **都按 uid 隔离**（`pending_sync:<uid>` / `last_server_seq:<uid>`）并落盘。单例队列会让 A 的改串到 B 账号；不落盘则 3 秒定时器没烧完就退出 App 会丢改动。 |
| 登出 | 只停定时器，**保留**各 uid 的积压队列，下次同一账号登录继续推。 |
| 团队列表 | 按 uid 缓存到 localStorage（`team_cache:<uid>`）。没有它，断网冷启动时团队列表为空，可见范围会退化成「只有我的私人菜谱」，家人的菜谱从列表里消失。 |
| 当前菜谱本 | `null` = 我的菜谱，否则是某个 teamId，存 localStorage。它只影响列表的 `WHERE` 条件，不改任何一行数据。 |

## 8. 常见问题排查

**1）同步一直失败，「我的」页显示「上次同步没成功」**

先看「我的」页那条红字，再按顺序查：

```bash
docker compose ps                                   # api 是不是 Up
docker compose logs api | tail -50                  # 服务端错误
curl -s <你填的地址>/api/v1/healthz                  # 客户端探活用的就是它
```

- `healthz` 通、App 还是报错 → 看路径：地址栏里**不要带 `/api/v1`**，填 `http://192.168.1.10:8080` 这种。
- 地址对但一直失败 → 401 通常是 token 过期且 refresh 也失败，退出登录重新登录一次。
- 服务端日志里是 `password authentication failed` → 容器的 `POSTGRES_PASSWORD` 与
  既有 `pgdata` 卷创建时的不一致（该变量**只在首次初始化数据库时生效**），改成当时的那个值即可。
- 网络本身不通（另一台设备连不上这台服务器）→ 检查服务器防火墙放行 8080。

**2）看不到家人的菜谱**

- 确认「我的」→「我的家庭」里能看到那个家庭（团队列表没加载出来，可见范围就没有它；断网时读的是本地缓存）。
- 确认菜谱列表顶部切到了那个家庭——切在「我的菜谱」上只看得到自己的私人菜谱。
- 刚加入家庭、而对方在你加入**之前**就录了菜谱 → 靠「加入后清游标、全量重拉」。
  加入成功后应立刻看到；看不到就在「我的」页点一次「重试」，还看不到就退出登录重登一次。
- 对方那条菜谱如果是**私人**的（没切到家庭就录了），任何成员都看不到，这是设计如此。

**3）封面是空白的**

- 服务端那批菜谱根本没有图 → 上传至少有一张失败，客户端会把**整批菜谱**都扣下（§6），
  所以家人那边「有菜谱但没封面」意味着你本机下次同步还会重试上传。检查本机图片文件是否还在
  （`$APPDATA/images/<name>`）、是否超过 5MB。
- 图曾经能看、后来变白 → 服务端的图被清理或卷被重建；`GET /files/{name}` 现在是 404。
  **客户端对 404 不重试**：这条菜谱已经落库，只有菜谱本身再次变化（`updated_at` 更新）时
  才会重新带出这条引用、重新排队下载。
- 压根没同步过图（比如只在桌面端 dev 里跑）→ 确认这台设备的 `$APPDATA/images/` 目录可写。

**4）改不了家人的菜谱**

设计如此，不是 bug。规则是「只有录的人能改能删」：非作者在详情页看不到编辑和删除按钮
（不是灰掉，是不渲染），服务端收到越权写入也会静默跳过。想改就自己新建一条。

**5）服务器库被重建，或恢复了一份旧备份**

- 服务端有世代护栏：`MAX(server_seq)` 低于客户端游标时，客户端自动按全量重拉一次，游标退回当前世代，不需要你做什么。
- 但**账号行若不在新库里**，`/me` 会 401、刷新令牌也失败 → 在 App 里**重新登录**（或重新注册），新账号从零开始同步；
  本机的菜谱会在认领后重新推上去。
- 图片是另一个卷，`docker compose down -v` 会连图一起删掉；只 `down` 不会。恢复图见 `SELF-HOSTING.md` 的备份一节。

**6）换手机后登录，本机原有的菜谱没上来**

只有当本地那条菜谱的 `owner_id` 是 NULL（本机自建、从未认领）时才会上推。
已被别的账号认领过的菜谱（例如同一台设备换人登录过）不会推给新账号。
另外确认这台设备的 `pending_sync:<uid>` 没被外部清掉——清掉也没关系，登录/恢复会话时的那次全扫推送会兜住。

## 9. 已知限制

按重要程度排，**都是刻意不做、不是漏做**：

1. **时钟偏差**。LWW 用的是记录里的 `updated_at`，客户端的时间快就会一直赢。
   更糟的是：**LWW 输掉的那次修改是无声丢弃的**——不提示、不保留历史、没有回收站。
   冲突只可能发生在「同一个人的两台设备」上（只有作者能改），所以没有做冲突解决。
2. **图片不做垃圾回收，也没有配额**。删菜谱不删图，换封面也不删旧图；孤儿图谁都读不了但占着磁盘。
   磁盘满了要自己清 `files` 卷。将来加 GC 时的依据是「还有没有菜谱引用它」（含软删菜谱）。
3. **团队只能建、不能管**：不能改名、不能解散、不能退出、不能移除成员、不能转让所有权。
   邀请码 6 位数字、24 小时有效，由 Redis 存，只由 owner 生成。
4. **菜谱不能换本**：一条菜谱要么是私人的，要么属于某个家庭，没有「搬进家庭 / 搬回私人」的界面。
   想换只能新建一条。
5. **菜谱被作者移出我的可见范围时，我本地会留一条陈旧副本**。
   作者把 `team_id` 改成别的家庭、或改成私人之后，我的客户端不会再收到这条菜谱的增量，
   也就既不能更新、也不能删除它——它会一直以旧内容留在我的列表里。要让它消失只能本机删行（改库）或清库重同步。
6. **子表整条替换**：改一次菜谱（哪怕只改一个字）会重传它的全部步骤与用料。家庭规模的数据量下可忽略。
   代码里留了 `shortcut:` 注释：将来允许协作编辑同一条菜谱时，必须回到行级 LWW（spec §7.3）。
7. **没有实时推送**，最长要等 3 秒防抖或下一次冷启动。
8. 字典是**全服务器共享**的，不分家庭：同一台服务器上任何登录用户都能改别人建的食材名。
   自托管假设是「一台服务器 = 一个家庭」。升级路径是给三张字典表加可空的 `team_id` 并按家庭过滤。

## 10. 人工验收清单（在真机 / 真 Tauri 窗口上做，自动化跑不了）

下面这些只能人工点，本轮**没有执行**，改动同步相关代码后请照单过一遍。

### 桌面端两个实例（两个不同的 `$APPDATA`，或一台真机 + 桌面端）

服务器地址填 `http://localhost:8080`（不带 `/api/v1`）。

| # | 操作 | 要看到什么 |
|---|---|---|
| 1 | A 注册 → 录一条带封面的私人菜谱 | 「我的」页显示上次同步时间；服务端库里有这条菜谱 |
| 2 | A 建家庭「我家」 | 拿到一个 6 位邀请码 |
| 3 | B 注册 → 输入邀请码加入 | **B 能看到 A 加入前录的团队菜谱**（游标清 0 的回归，没清就是空的且不报错） |
| 4 | A 录一条团队菜谱（带封面） | B 能看到且**封面能显示**（图片通道通） |
| 5 | B 打开 A 的菜谱详情 | **没有**编辑与删除按钮 |
| 6 | B 断网 → 录一条私人菜谱 + 改字典 → 恢复网络 → 同步 | A 看不到 B 的私人菜谱；B 的改动同步上去了 |
| 7 | A 的两台设备改同一条菜谱 | 同步后两边都是较新的那份（LWW） |

### Android 真机

```bash
npm run tauri android dev
```

- 真机上能登录、能同步、能下载封面。
- 真机的 CORS 与明文 HTTP 与桌面 dev 不同，必须在真机上过一遍。
