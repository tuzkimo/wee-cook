# 数据库与图片备份 + NAS 异地拉取指南

> 适用对象：没有运维经验也能照着操作。本文教你在云服务器上每天自动备份数据库和图片（滚动保留最近 7 天），再让家里的 NAS 每天把备份拉回本地留一份。
>
> 需要你替换的只有下面几个值（其余路径都有默认值，跟着抄就能跑；想改看 1.3 和 2.4）：
> - `<用户名>`：服务器上 SSH 登录用的用户名
> - `<服务器内网地址>`：服务器在 EasyTier 里的虚拟 IP
> - `<SSH端口>`：SSH 端口，默认 22（**不是 22 才需要替**，见 2.2、2.4）

## 0. 最终效果

```text
云服务器（每天 03:30）                        NAS（每天 04:30）
┌──────────────────────────────┐             ┌──────────────────────────────┐
│ 1. pg_dump 导出数据库         │             │ 1. rsync 从服务器拉文件       │
│ 2. 打包 files 卷里的图片      │  EasyTier   │ 2. 存到本地目录               │
│ 3. 存成 .sql.gz + .tar.gz    │◄─── VPN ────│ 3. 删掉 30 天前的旧备份       │
│ 4. 删掉 7 天前的旧备份        │             │                              │
└──────────────────────────────┘             └──────────────────────────────┘
     保留最近 7 天                                保留最近 30 天
```

两边各自滚动清理，**服务器只留 7 天（省磁盘），NAS 留 30 天（要留久一点）**。就算服务器被人删了库，NAS 上还有 30 天内的副本。

**每天产出两个文件，必须一起备份**：数据库里只存图片的**文件名**，图片本体在 `files` 卷里。只备份数据库，恢复后菜谱全在、图片全裂 —— 所以要两个一起拿、一起恢复。

用到的两个脚本都在本仓库里：

| 脚本 | 放哪 |
|------|------|
| `scripts/backup-db.sh` | 云服务器（仓库里就有，跟着 `git pull` 更新） |
| `scripts/nas-pull-backup.sh` | NAS 上（NAS 没有仓库，装一份，见 2.4） |

## 1. 服务器侧：每天自动备份

> 以下命令都在**云服务器**上执行（SSH 登录后），用运行部署的那同一个账号。

### 1.1 把脚本取下来

仓库里的脚本随 `git pull` 一起来。项目目录按你实际部署的位置（下例假设在 `~/wee-cook`）：

```bash
cd ~/wee-cook && git pull
chmod +x scripts/backup-db.sh        # 万一提示 Permission denied 就执行这句
mkdir -p ~/backup                    # 放日志，脚本第一次跑也会自己建备份子目录
sudo apt update && sudo apt install -y rsync   # 推荐装（Debian/Ubuntu 系）：rsync 拉取需要两端都有 rsync
```

> 脚本放在仓库根的 `scripts/`（不在 `backend/`）是故意的：`backend/**` 一改动就会触发 GitHub 重新构建并部署后端，改个运维脚本不该顺带重启生产。
>
> 脚本顶部有「可调参数」几行，默认值直接能用，先不用管。
>
> **服务器没装 `rsync` 也不会挂**：2.4 的脚本会自动改用 `tar`（两端系统自带）把备份取回来，代价是每次全量重传。想省流量就在服务器上装一下 rsync（就是上面那行）。

`backup-db.sh` 干的事（就这四步）：

1. 在 `docker compose` 的 `postgres` 容器里跑 `pg_dump`，导成 `.sql.gz`；
2. 从运行中的 `api` 容器反查 `files` 卷的真实名字（`<项目名>_files` 随部署目录变，写死会踩坑，见 FAQ），把图片打包成 `.tar.gz`；
3. 两份都先写临时文件，自检通过（压缩包完整 + 里面确实是 pg_dump 输出 / tar 包）才改成正式名字；
4. 文件名带日期，同一天重跑直接覆盖，不堆积；删掉 7 天前的旧备份。任何一步失败都会留下明确报错、不产生坏备份。

### 1.2 手动跑一次，确认能用

```bash
~/wee-cook/scripts/backup-db.sh
```

期望输出（最后一行有日期和两个文件大小就对了）：

```text
2026-01-01 03:30:12 OK 数据库 /home/<用户名>/backup/wee-cook/wee-cook-2026-01-01.sql.gz 1.2M / 图片 /home/<用户名>/backup/wee-cook/wee-cook-files-2026-01-01.tar.gz 63M
```

再确认文件不是空壳：

```bash
ls -lh ~/backup/wee-cook/
zcat ~/backup/wee-cook/wee-cook-*.sql.gz | head -3      # 应看到 -- PostgreSQL database dump
tar -tzf ~/backup/wee-cook/wee-cook-files-*.tar.gz | head    # 应列出 ./ 和一堆 .jpg/.png 文件名
```

**如果文件只有几十字节、或者这两条命令报错，先别往下做**，把报错贴出来。

> 图片包**只有 `.` 一行**也是正常的 —— 那是新装的服务器还没人传过图。真有图之后应该是几十 MB 起。

### 1.3 要改参数？改脚本顶部那几行（默认可直接跳过）

默认值就是本文用的这套（备份到 `~/backup/wee-cook`、留 7 天），**不用改**。想改的话，用编辑器打开脚本，改最上面那一段：

```bash
nano ~/wee-cook/scripts/backup-db.sh
# 改完按 Ctrl+O 回车保存，Ctrl+X 退出
```

```bash
# ====== 可调参数 ======
COMPOSE_DIR=$(cd "$(dirname "$0")/.." && pwd)   # compose.yml 所在目录（仓库根）；脚本放仓库 scripts/ 里就不用改
BACKUP_DIR=$HOME/backup/wee-cook   # 备份存哪
KEEP_DAYS=7                        # 保留最近几天
PG_SERVICE=postgres                # compose.yml 里的数据库服务名
API_SERVICE=api                    # 挂着图片卷的服务
# =====================
```

> 这个文件是 git 管理的。改过之后，下次 `git pull` 如果恰好也改了这个文件会提示冲突；碰到就执行 `git checkout -- scripts/backup-db.sh` 放弃本地改动（git pull 完再改一遍），或干脆把脚本复制到仓库外面用（复制出去的话，把 `COMPOSE_DIR` 改成指向仓库根目录）。
>
> 改了 `BACKUP_DIR` 的话，**2.4 里 NAS 脚本顶部的 `REMOTE_DIR` 也要跟着改**（填服务器上家目录的相对路径，或直接填绝对路径）。

### 1.4 交给 cron 每天自动跑

```bash
crontab -e
```

第一次会让你选编辑器，选 `nano`（数字最小的那个）最简单。在文件末尾加一行：

```cron
30 3 * * * $HOME/wee-cook/scripts/backup-db.sh >> $HOME/backup/backup.log 2>&1
```

保存退出（nano：`Ctrl+O` 回车，再 `Ctrl+X`）。

- `30 3 * * *` 意思是每天凌晨 3:30（按**服务器所在时区**算）。
- 后面那串表示把每次运行的输出追加写进 `~/backup/backup.log`，出问题时有据可查。

确认写进去了：

```bash
crontab -l
```

第二天再看一眼日志和目录，两条都正常就说明自动备份跑通了：

```bash
tail -5 ~/backup/backup.log
ls -lt ~/backup/wee-cook/ | head
```

## 2. NAS 侧：每天把备份拉回家里

> 以下命令在 **NAS** 上执行（SSH 登录你的 Debian NAS）。
> 先装齐要用的几个命令（已经有了会提示 already installed，可以忽略）：
> ```bash
> sudo apt update && sudo apt install -y rsync openssh-client cron curl
> ```

### 2.1 先确认两台机器真的通

在 NAS 上 ping 服务器的 EasyTier 地址（EasyTier 的虚拟 IP 通常是 `10.126.x.x` 这类，在服务器上执行 `easytier-cli peer` 能看到）：

```bash
ping -c 3 <服务器内网地址>   # 报 command not found 就先 sudo apt install -y iputils-ping
```

通不了就先解决 VPN 的事，后面所有步骤都会失败。

### 2.2 给 NAS 配一把钥匙（免密码登录）

NAS 要能自动登录服务器，用的是「公钥」而不是密码。下面的定时任务用 root 跑，所以钥匙就放在 root 家目录里：

```bash
sudo mkdir -p /root/.ssh && sudo chmod 700 /root/.ssh
sudo ssh-keygen -t ed25519 -f /root/.ssh/wee_cook_pull -N ''
sudo cat /root/.ssh/wee_cook_pull.pub
```

把最后一条命令输出的**一整行**复制下来（`ssh-ed25519 AAAA...` 开头），然后回到**服务器**上执行（把粘贴的内容替换掉 `<刚复制的那一行>`）：

```bash
echo '<刚复制的那一行>' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

回 NAS 测试免密登录（**不应该再问密码**）：

```bash
sudo ssh -p <SSH端口> -i /root/.ssh/wee_cook_pull <用户名>@<服务器内网地址> 'ls -lt ~/backup/wee-cook | head -3'
```

能看到备份文件名就成功了。第一次会问 `Are you sure you want to continue connecting?`，输入 `yes`。

> **SSH 不是 22 端口的话**，`-p <SSH端口>` 不能省（默认 22 可以写成 `-p 22` 也可以删掉）。这个端口等会要填到 2.4 脚本的 `SSH_PORT` 里，两处必须一致。

> 这一次测试不能省：它会把服务器的指纹记进 `/root/.ssh/known_hosts`。脚本里带了 `-o BatchMode=yes`（不问密码、不交互），指纹没记录过的话自动化会直接失败。用 `-o BatchMode` 是为了让「要输密码」这类情况立即报错，而不是挂着等输入把 cron 卡死。

### 2.3 建备份目录（必须在数据盘上）

先定好备份存哪个目录。**本文统一用 `/srv/backup/wee-cook` 演示，跟着抄最省事**。你的数据盘若挂在别的地方（比如 `/mnt/data`），就把它换成 `/mnt/data/backup/wee-cook`，并且：目录建在数据盘上、2.4 的配置里填这个路径、2.6 的 cron 里脚本路径不用动。

```bash
sudo mkdir -p /srv/backup/wee-cook
df -h /srv/backup/wee-cook
```

> ⚠️ `df` 输出的 `Mounted on` 一列必须指向你的**数据盘**。如果显示 `/`（根分区），说明这个目录还在系统盘上，换成数据盘的路径再来——否则数据盘没挂载时，备份会静默写到系统盘把系统盘写满（脚本里那个 `[ -d ... ]` 检查就是防这个）。

### 2.4 装脚本 + 改顶部几行

脚本就一份，直接从这个仓库下载（**不用手抄**）。NAS 上没有仓库，所以下载到系统目录：

```bash
sudo curl -fsSL https://raw.githubusercontent.com/tuzkimo/wee-cook/main/scripts/nas-pull-backup.sh \
  -o /usr/local/bin/wee-cook-pull-backup.sh
sudo chmod +x /usr/local/bin/wee-cook-pull-backup.sh
```

然后是唯一必须做的一步 —— 改顶部那两行：

```bash
sudo nano /usr/local/bin/wee-cook-pull-backup.sh
```

```sh
# ====== 必须改 ======
SERVER=<用户名>@<服务器内网地址>     # 服务器的 SSH 登录名@EasyTier 地址
BACKUP_DIR=/srv/backup/wee-cook       # 2.3 里建的目录；建在别处就改成那个路径
# ====================

# ====== 按需改 ======
SSH_PORT=22                          # 服务器的 SSH 端口，不是 22 就改（同 2.2）
TRANSFER=auto                        # 一般不用动；auto = 两端有 rsync 就用 rsync，否则自动用 tar
# ====================
```

改完按 `Ctrl+O` 回车保存，`Ctrl+X` 退出。

> 忘了改 `SERVER` 的话，跑脚本会直接提醒你；`SSH_PORT` 填错会报 `Connection refused`（端口错）或 `Permission denied`（端口对了但密钥没配好）。
>
> 以后脚本本身更新了，**重新执行一遍上面那两条 `curl` + `chmod`，再把顶部两行改回来**即可（`curl` 会把文件整个覆盖，你的改动也一起没了）。

脚本其余部分（`TRANSFER` / `KEEP_DAYS` / `REMOTE_DIR` / `SSH_KEY`）的含义都在注释里，默认值正好对上本文的路径，不用动。

### 2.5 手动跑一次，确认能拉到

```bash
sudo /usr/local/bin/wee-cook-pull-backup.sh
ls -lh /srv/backup/wee-cook/
```

目录里出现和服务器上同名的 `wee-cook-*.sql.gz` 和 `wee-cook-files-*.tar.gz` 就成功了。

### 2.6 加到定时任务

Debian 用 cron。先确认 cron 在跑：

```bash
sudo systemctl enable --now cron
systemctl status cron --no-pager | head -3
```

看到 `active (running)` 就对了。然后编辑 **root 的 crontab**：

```bash
sudo crontab -e
```

第一次会让你选编辑器，选 `nano`（数字最小的那个）。在文件末尾加一行：

```cron
30 4 * * * /usr/local/bin/wee-cook-pull-backup.sh >> /var/log/wee-cook-pull.log 2>&1
```

保存退出（nano：`Ctrl+O` 回车，再 `Ctrl+X`），确认写进去了：

```bash
sudo crontab -l
```

- `30 4 * * *` = 每天凌晨 4:30（比服务器备份晚 1 小时，留足时间；也按 NAS 自己的时区算）。
- 结尾那段重定向必须留着：cron 默认想把输出邮寄给用户，而家用 NAS 一般不装邮件服务，报错会被直接丢掉。日志写到 `/var/log/` 而不是跟着备份放，万一数据盘没挂上也不会悄悄写到系统盘里。
- 想手动试一次不用等到 4:30，直接 `sudo /usr/local/bin/wee-cook-pull-backup.sh`，效果一样。

> cron 自己干活的痕迹在 `/var/log/syslog` 里：`grep CRON /var/log/syslog | tail -5`（Debian 12 及以后也可能在 `/var/log/cron.log`）。

### 2.7 （可选，更安全一点）

上面那把钥匙等于给了 NAS 一个能登录服务器的账号。如果 NAS 被人拿到，攻击者也能登上服务器。想收紧的话，在**服务器**的 `~/.ssh/authorized_keys` 里把 NAS 的那一行前面加上限制（路径要和服务器脚本里的 `BACKUP_DIR` 一致）：

```text
restrict,command="rsync --server --sender -logDtpre.iLsfxCIvu . /home/<用户名>/backup/wee-cook/" ssh-ed25519 AAAA...那一行剩下的部分
```

这样这把钥匙只能用来拉备份目录，不能开 shell、不能端口转发。（SSH 端口改过也不影响这一行。）

两个注意点：

- 加了之后 2.2 里那个 `ssh ... 'ls -lt ...'` 测试命令就不能用了，改用跑脚本的方式验证。
- 不同 rsync 版本的 `command=` 字符串可能不一样。加完**先在 NAS 上手动跑一次拉取**，报错了就把 `command="..."` 去掉、只留 `restrict`（去掉 SSH 转发能力，仍能防一部分滥用）。

## 3. 日常：怎么确认它还活着

备份最危险的不是报错，而是**悄悄停了没人知道**。每周花 10 秒看一眼：

| 在哪台机器 | 命令 | 正常应该看到 |
|------------|------|--------------|
| 服务器 | `tail -3 ~/backup/backup.log` | 最新一行是今天的日期，带 `OK` |
| 服务器 | `ls -lt ~/backup/wee-cook/ \| head -4` | 最新两个文件是今天的（`.sql.gz` 和 `-files-*.tar.gz`），共 14 个 |
| NAS | `sudo tail -3 /var/log/wee-cook-pull.log` | 最新一行是今天的日期，带 `OK` |
| NAS | `ls -lt /srv/backup/wee-cook/ \| head -4` | 最新文件是今天的 |

**如果服务器上有日志、NAS 上没有**：说明 VPN 或钥匙的问题，手动在 NAS 上跑一次脚本看报错（多半是 `ping` 不通或钥匙没配对）。

**如果两边日志都停在几天前**：检查 cron 是否还在（服务器/NAS 各自 `crontab -l`）、NAS 上 `systemctl status cron` 是否 active、以及服务器上 `docker compose ps` 数据库容器是否正常。

## 4. 真出事时怎么恢复

### 4.1 恢复线上数据库

> ⚠️ 这会把数据库恢复成备份那一刻的状态，**之后新产生的数据会丢**。只在确实需要回滚时做。
>
> **不要把备份直接灌进已经有数据的库**：那会报一堆 `already exists`，最后库里是「旧的+新的」混在一起，比恢复之前更难收拾。正确做法是先把库清空再灌。

在**服务器**上依次执行（`BACKUPS` 是服务器脚本里的备份目录；文件名换成你要恢复的那个）：

```bash
BACKUPS=$HOME/backup/wee-cook
FILE=$BACKUPS/wee-cook-2026-01-01.sql.gz
cd ~/wee-cook

# 1. 先停后端，避免恢复过程中还在写数据
docker compose stop api

# 2. 把「现在的状态」另存一份，万一恢复错了还能退回去
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' | gzip > /tmp/before-restore.sql.gz

# 3. 清空并重建数据库
docker compose exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'

# 4. 灌入备份（ON_ERROR_STOP=1 表示碰到任何错误就立刻停，不会闷头跑出一个残缺的库）
gunzip -c "$FILE" | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

# 5. 把后端起回来
docker compose start api
```

第 4 步唰唰输出一堆 `CREATE TABLE`、`COPY` 是正常的。报错了就别继续，把报错贴出来。

> 上面的命令不用管用户名和库名：它们直接取容器里的 `POSTGRES_USER` / `POSTGRES_DB`，你改过 `.env` 也照样对。

### 4.2 恢复图片

数据库只存文件名，图片得单独放回 `files` 卷。**和 4.1 用同一个日期的备份**，否则菜谱会指向不存在的图。

```bash
FILES=$HOME/backup/wee-cook/wee-cook-files-2026-01-01.tar.gz
cd ~/wee-cook

# 卷名从运行中的 api 容器反查，不用猜项目名
VOL=$(docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data/files"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps -q api)")

gunzip -c "$FILES" | docker run --rm -i -v "$VOL":/data postgres:16-alpine tar xzf - -C /data
```

- 这是**覆盖同名文件**：卷里已有的图不会被动，多出来的孤儿图也不会被删。只想补齐丢失的图，这就够了。
- 想彻底换成备份里的状态，先 `docker compose down`（**别加 `-v`**，那会连卷一起删），再把卷清空后恢复。清空卷是不可逆的，动手前先确认备份包 `tar -tzf` 能正常列出来。

### 4.3 先演练一次（强烈建议）

备份到底能不能恢复，**没演练过就不算验证过**。演练不影响线上数据：起一个一次性的空数据库/空卷，把备份灌进去看看有没有数据。用的是服务器上已经有的镜像，不会额外下载东西。

```bash
LATEST=$(ls -t $HOME/backup/wee-cook/wee-cook-*.sql.gz | head -1)

docker run -d --name pg-drill -e POSTGRES_PASSWORD=drill -e POSTGRES_USER=wee -e POSTGRES_DB=wee-cook postgres:16-alpine

# 等这个临时库真正启动（最多等 60 秒）
for i in $(seq 1 30); do docker exec pg-drill pg_isready -U wee > /dev/null 2>&1 && break; sleep 2; done

# 灌备份：没有报错、没有输出就是正常的
gunzip -c "$LATEST" | docker exec -i pg-drill psql -v ON_ERROR_STOP=1 -U wee -d wee-cook > /dev/null
docker exec -i pg-drill psql -U wee -d wee-cook -c 'select count(*) from users;'
docker exec -i pg-drill psql -U wee -d wee-cook -c 'select count(*) from recipes;'

docker rm -f pg-drill   # 演练完删掉临时容器，不留垃圾
```

`count` 出来的数字和你 App 里的用户数 / 菜谱数对得上，就说明备份是**真的能恢复**的。建议每季度做一次。

图片包也可以顺手验一下（灌进一个临时卷，看文件数对不对，然后删掉）：

```bash
FILES=$(ls -t $HOME/backup/wee-cook/wee-cook-files-*.tar.gz | head -1)
docker volume create files-drill
gunzip -c "$FILES" | docker run --rm -i -v files-drill:/data postgres:16-alpine tar xzf - -C /data
docker run --rm -v files-drill:/data postgres:16-alpine sh -c 'find /data -type f | wc -l'
tar -tzf "$FILES" | wc -l          # 两个数字应该只差 1（tar 包里多一行 ./）
docker volume rm files-drill
```

> 演练里的 `wee` / `wee-count` 要和 `.env` 里的 `POSTGRES_USER` / `POSTGRES_DB` 一致。如果你改过这两个值，把上面两条 `-e` 和两条 `psql -U/-d` 一起改；否则 dump 里的对象属主找不到对应角色，第三步会报错停下。

### 4.4 恢复完还要做什么

- 服务端有世代护栏：库里没有的客户端游标会被要求**全量重拉**，客户端首次同步会自动重来一遍。
- 备份里没有的账号，客户端会 `401` → 刷新令牌也失败 → 自动登出，需要**重新注册/登录**（新账号从零同步）。所以恢复旧的数据库 = 那之后注册的账号全没了。
- 详细口径见 [自托管指南](SELF-HOSTING.md) 的「备份」一节和 [开发者-同步与社区](开发者-同步与社区.md)。

## 5. 常见问题

**Q: 备份文件多大算正常？**
数据库包几百 KB 到几 MB 都正常。图片包跟着你传的图走，几十 MB 不奇怪。突然变成几十字节说明那次备份失败了，去翻日志。

**Q: 图片包每天都在长，正常吗？**
正常。删菜谱**不会**删图片（服务端没做引用计数与垃圾回收），图片只增不减，所以包会持续变大。真觉得占地方就把服务器脚本的 `KEEP_DAYS` 从 7 改成 3。

**Q: 同一天跑了两次会怎样？**
文件名带日期，第二次直接覆盖第一次，不会堆积——这也是用日期命名而不是时间戳的原因。

**Q: 服务器磁盘被备份撑爆了？**
数据库包不用担心。图片包大的话，把服务器脚本顶部的 `KEEP_DAYS` 改小（比如 3），日志、备份目录一把 `du -sh ~/backup` 就能看清。

**Q: NAS 上想留更久？**
同样改脚本顶部的 `KEEP_DAYS`（比如 `90`）。两台机器上的脚本各改各的，互不影响。

**Q: 只想备份数据库，不想要图片？**
那就别用这个脚本，手敲 `docker compose exec -T postgres pg_dump -U wee wee-cook | gzip > xxx.sql.gz`。但要清楚代价：恢复后所有图片链接都是断的。真嫌图片包大，更好的做法是把 `KEEP_DAYS` 调小，而不是不备图片。

**Q: 手动 `docker run -v` 打包图片，为什么打出来是空的？**
卷名写错了。真实卷名是 `<compose 项目名>_files`，项目名默认取自 `compose.yml` 所在目录名，`docker run -v` 遇到不存在的卷名**不报错**，会新建一个空卷然后打包出空归档。用 `docker volume ls | grep files` 确认，或者直接用 `scripts/backup-db.sh`（它从运行中的容器反查，不用你猜）。

**Q: 服务器上没装 rsync 会怎样？**
脚本会自动改用 `tar` 传（两端系统自带），能用，只是每次把全部备份重传一遍。NAS 的日志（`/var/log/wee-cook-pull.log`）里会写一行 `传输方式：tar`，看到就说明走的退路。想用 rsync 就在服务器上 `sudo apt install -y rsync`。

**Q: SSH 不是 22 端口？**
把脚本顶部的 `SSH_PORT` 改成实际端口（2.2 的手动测试命令也要带 `-p`）。忘了改的典型报错是 `Connection refused`。

**Q: 服务器 cron 日志里写 `docker: command not found`？**
cron 的 `PATH` 比登录 shell 小得多。在 crontab（服务器那份）顶部加一行 `PATH=/usr/local/bin:/usr/bin:/bin`，再重新跑一次即可。

**Q: 服务器 cron 日志里写 `permission denied`？**
脚本没有可执行权限（git 里没带上），`chmod +x ~/wee-cook/scripts/backup-db.sh` 一下就行。

**Q: 能不能让 App 的本地数据也备到服务器？**
不在本文范围。客户端是离线优先的本地 SQLite，数据不出设备，这是设计约定。
