## 1. 目标与范围

一句话：**把散落在小红书 / 下厨房的菜谱，用一张长截图搬进本地库，变成跟手动录入一模一样的结构化菜谱；再让你用一句话把它们找出来。**

两个入口：

- **聊天检索**：在 `/ai` 说一句话（语音由系统输入法完成）→ 翻译成本地筛选条件 → 结果以菜谱卡片列出
- **长截图收录**：小红书长截图 → 分享进 App → AI 识别 → **预填菜谱编辑页** → 用户改完保存

**明确不做（YAGNI）**：

- **AI 凭自己的知识编写菜谱**。2026-10-16 用户决策：宁可搜不到，不要一份用量和火候都是编的菜谱
- AI 修改 / 删除已有菜谱（红线：只读 + 只生成待确认的新菜谱）
- 语音识别。系统输入法自带，自写录音权限 + 原生桥 + 机型兼容成本不对等（沿用主规格 §10.8 的同类判断）
- **互联网搜菜谱**。小红书 / 下厨房反爬，服务端抓不到——这正是截图这条路存在的理由
- 视频 / PDF（动图只取首帧，见 §8）
- 社区菜谱进 AI 检索范围，见 §7.1
- 聊天记录与截图参与同步（沿用主规格 §10.5）
- 流式输出、图表卡片、多会话列表、会话搜索
- 为封面图单独调模型
- 「按食材反向推荐」「缺料计算」（筛选规格里已列为非目标，AI 不复活它）

## 2. 现状约束（已核实的探索结论）

**客户端**

- `src/views/AiPage.vue` 是 12 行占位页；`/ai` 已在 `src/router/index.ts` 注册，已是 `App.vue` 三个 tab（菜谱 / AI / 我的）里的**第 2 个**，**无条件显示**（没有任何门控）
- **`recipeFilter` 已经有这四维**：关键词、分类多选、标签多选、食材多选；跨维度是「并且」，食材维度内是「同时包含」（筛选规格 §5、§6.1）⇒ **AI 只需产出这个对象，零新增检索逻辑**
- 筛选页的候选项是**从已加载的菜谱里推导**（筛选规格 §6.1 决策 8），不是全量字典
- **筛选是内存纯函数**：`src/utils/recipeFilter.ts` 的 `filterRecipes()` 过滤 `recipeStore.recipes`（`RecipeListItem` 已带分类、标签、食材），**现状里没有任何过滤 SQL**
- `stores/recipe.ts` 的 `fetchAll()` 走 `visibleRecipeFilter()`，**只取自己名下 / 未认领的**菜谱；收藏来的别人菜谱在单独的 `store.favorites` 里，不在 `recipes` 里
- `RecipeEdit.vue` 是录入/编辑共用页，新建走 `/recipe/new`；`form` 是页面内的 `ref<Form>`，字段 `name / cover_path / category_id / is_public / tag_ids / steps / ingredients`；**页面只做输入清洗**（菜名 trim、空步骤丢弃、剥本地 key），`requireNameAndCategory` 在 `stores/recipe.ts` 的 `create` / `update` 里
- `src/services/api.ts`：`hasBaseUrl()` 是唯一的网络就绪判据，未配地址时不得发任何请求；`apiFetch` 拿不到 HTTP 响应时**抛异常**，`ApiResult.status` 只会是真实状态码
- `settingsFile.ts` 是 `settings.json` 的唯一读写层（服务器地址、登录信息都在里面）；`src/views/MePage.vue` 是「我的」页，**目前没有隐私设置区块**（那是 wee-count 的 `SecurityPage`）⇒ 本设计的隐私开关是**净新增 UI**
- 图片走 `imageStore.ts`（本地文件）与 `/files` 上传

**本地数据**

- `recipes(id, name, cover_path, category_id, is_public, owner_id, owner_nickname, owner_avatar_url, created_at, updated_at, deleted_at)`
- `recipe_steps(id, recipe_id, sort_order, text, image_path, updated_at, deleted_at)`
- `recipe_ingredients(id, recipe_id, ingredient_id, amount, unit_id, sort_order, updated_at, deleted_at)`
- `recipe_labels(recipe_id, label_id)`；`labels(id, name, kind)`
- `ingredients(id, name, created_at, updated_at, deleted_at)`；`units(id, name, ...)`
- 唯一索引 `idx_ingredients_name` / `idx_units_name` / `idx_labels_name_kind`（均 `WHERE deleted_at IS NULL`）
- **`ingredients` 只有 `name`，没有别名表。** AGENTS.md 说的「别名由食材表归一」= 同一物归并到同一行；匹配只能靠字符串
- 本地 schema 演进走 `src/db/index.ts` 的 `migrateTables`（先 `PRAGMA table_info` 再 `ALTER`，不能靠异常兜底）

**后端**

- chi 路由 `/api/v1`；`middleware.AuthMiddleware` 把 user id 放进 ctx；已有 `handler/{auth,community,files,sync}.go`、`service/*`、`model/*`
- `config.Load()` 对 `DATABASE_URL / REDIS_URL / JWT_SECRET` 缺失即 `log.Fatalf`
- 同步是**显式列举表名**的（`sync.ts` 的 `SyncPayload` 逐表列举；`migration.ts` 只做无主认领与触发一次全扫，**不**列举同步表）⇒ 新表天然不进同步，但这是隐式安全，必须用测试钉住（沿用主规格 §2 的同款判断）
- 服务端**本来就有菜谱数据**：`model/recipe.go` 定义了完整菜谱与子行，`handler/sync.go` + `service/sync.go` 收下发，`handler/community.go` 读公开菜谱。本文说的「AI 后端不读菜谱数据」是**新加的自我约束**，不是现状

## 3. 关键决策记录

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 部署形态 | **自托管后端代理**（沿用主规格 §3 方案 A） | 家人零配置、共享一份 key、客户端不碰 key；契合 SELF-HOSTING 定位 |
| AI 权限边界 | **只读 + 只生成待确认的新菜谱** | 误操作代价最小 |
| 自然语言 → 检索 | **受限筛选对象 + 工具调用** | 结果永远来自本地 SQL；模型不碰数据 |
| 模型给名字还是 id | **只给名字，本地解析** | 让模型抄 UUID 是幻觉第一大来源（主规格 §3） |
| **识别结果的落点** | **预填 `RecipeEdit` 表单**，不是只读草稿卡 | 用户明确要「跟手动录入的一样」。这同时是最省的做法：同一个表单、同一条保存路径、零新组件。与主规格 §4.4 的「只读草稿卡」**有意偏离**——账单是一串数字、改它不如重来；菜谱是二十个字段的文档，改它才是常态 |
| **分享进 App 的实现** | **移植分享目标规格**，不重新设计 | 那份规格已把 `MainActivity.kt` 的冷 / 热启动、`pending.json` 的 compare-and-delete、与会话自动锁的交叉逐个钉死。从零踩一遍的代价是丢分享、重复投递、每次分享都要求解锁 |
| 截图发给上游的形状 | 沿用 M4 §4.2：`image_url` 内容块；历史里替换为占位符 | 已验证 |
| **长截图的缩放规则** | **按宽度缩放 + 分段**（与 M4 的「最大边 1280px」**有意偏离**） | 长截图纵横比可达 1:10，按最大边缩到 1280px 会让正文文字不可读。M4 的量是"一张小票"，这里是一整页笔记 |
| 封面图 | **裁长截图的第一屏**，跳编辑页**之前**写进 `imageStore` | 小红书笔记首图就是菜品图；先落盘再跳页，「草稿槽读走即清」不会留下无主的封面引用 |
| 食材 / 单位未命中 | 不静默新建、不静默丢弃，带进编辑页让用户落定（§4.4） | 见 §4.4 |
| 聊天记录同步 | **永不参与同步** | 同主规格 §10.5 |
| 模型 | **一个 `AI_MODEL`，默认 `deepseek-flash`** | 它同时支持视觉与工具调用（官方定价页与 vision 指南均确认）；拆成两个键只多一个「配错一半」的失败模式 |
| 流式 | v1 不做 | 同主规格 §6.4 |
| `/ai` tab 显隐 | **客户端 opt-in 是唯一开关**：关着才隐藏；探活处于未知态**不隐藏**；只有服务端明确回 `enabled:false` 才隐藏 | 入口规格 §5 明确推翻了「后端没配 ⇒ 入口隐藏」——那会把一次断网误判成「功能没启用」，且用户找不回来 |

## 4. 数据契约

### 4.1 检索对象：直接复用 `RecipeFilter`

```ts
// 已存在于 src/utils/recipeFilter.ts（注意字段是 tagIds，不是 labelIds），本设计不新增类型
{ keyword: string; categoryIds: string[]; tagIds: string[]; ingredientIds: string[] }
```

模型输出的是**名字数组**，不是 id；名字 → id 的解析在本地完成（§4.4）。理由同主规格 §3：抄 UUID 是幻觉第一大来源。

**检索怎么跑**：先 `await recipeStore.fetchAll()`，再调 `filterRecipes()` —— 就是列表页与筛选页用的那个内存纯函数。**不写新的过滤 SQL**（现状里根本没有过滤 SQL，见 §2）。两个后果要认：

- 被 `visibleRecipeFilter()` 挡在外面的（别人名下、未认领）与收藏来的社区菜谱**不进检索**。这正是 §7.2 的结论，不是巧合
- `matched` = `filterRecipes()` 的结果长度，`applied` = 解析后的 `RecipeFilter`。两者都来自本地，与筛选页对同一个 filter 的结果**逐条一致**

### 4.2 工具契约（两个，v1 不加第三个）

**`search_recipes({ keyword?, categories?, labels?, ingredients? })`** —— 只读。

返回给模型的是摘要，给用户看的是卡片（卡片由本地 SQL 的真实数据渲染，模型不参与）：

```jsonc
{
  "matched": 3,
  "items": [
    { "name": "红烧肉", "category": "家常菜", "tags": ["下饭"],
      "ingredients": ["五花肉", "冰糖", "生抽"] }
  ],
  "unresolved": { "ingredients": ["三层肉"], "labels": ["快手"] },
  "applied": { "keyword": "", "categories": ["家常菜"], "ingredients": ["五花肉"] }
}
```

- **`matched` 统计的是本地真实命中数**，`items` 最多 10 条（卡片列表本来也看不完）
- **不需要数值引用占位符**（与主规格 §7.2 **有意偏离**）。主规格要用占位符，是因为账单里的数字错了就是错的；这里的真值是**卡片本身**，它由本地 SQL 渲染，模型说什么都不改变它。让模型写引用只会平白多一套前端回填机制
- `unresolved` 列出没对上的名字，让模型能自然地说「没找到『三层肉』，我按『五花肉』找的」
- **模型绝不返回任何菜谱正文**（步骤、用量）。它只配说「找到 3 道」

**`create_recipe_draft({ name, category?, tags?, ingredients?, steps? })`** —— 只往内存草稿槽塞一份预填数据并跳转编辑页，**绝不写库**。

```jsonc
{
  "name": "香辣土豆片",
  "category": "家常菜",
  "tags": ["下饭", "快手"],
  "ingredients": [
    { "name": "土豆", "amount": 2, "unit": "个" },
    { "name": "豆瓣酱", "amount": null, "unit": null }
  ],
  "steps": ["土豆去皮切片", "热锅下油，炒香豆瓣酱", "下土豆片翻炒 5 分钟"]
}
```

- `steps` 是**纯文本数组**。截图里的步骤配图**不提取**（AI 拿不到原图，切出来的图会带小红书水印与 UI 残渣）。步骤图由用户在编辑页补，或直接不做
- 字段名与 `RecipeInput` 对齐：`ingredients[].name` / `amount` / `unit`
- **工具描述里必须写明**：「菜谱已生成草稿，等你确认保存；你不得声称已经收录成功」——同主规格 §4.2 那条，不写这句模型会说「已经帮你存好了」
- 全空的识别结果（模型看不出这是菜谱）⇒ **模型不调工具**，直接回一句说明。客户端据此不跳转

### 4.3 发给模型的形状

- **文本轮**：`content` 是纯文本（同 M4 §4.2 的无图分支）
- **截图轮**：同一条 user 消息里，`content` 是内容块数组：
  ```jsonc
  [ { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,..." } },
    { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,..." } },   // 分段后的第二块
    { "type": "text", "text": "<用户随图附的一句话；没有则整个块不出现>" } ]
  ```
  - **分段是客户端内部行为，用户侧永远只发一张图。** M4「一条消息多张图不做」约束的是**用户输入**，不是发给模型的消息形状
  - 分段的每一块都发在同一轮里，模型能看到跨段上下文（一道菜的做法可能跨段断开）
  - 没写字时不出现空 `text` 块（空 `text` 块在部分供应商上被判非法，M4 §4.2）
- **历史替换**：截图轮在拼上下文时替换为 `[用户发过一张菜谱截图]`（有文字则 `[用户发过一张菜谱截图] <原文字>`）。图片不重发
- **图片只能出现在 `user` 消息里**——上游硬约束：`system` / `assistant` 消息里带图直接 400。当前流程天然满足（历史替换又恰好避开了这个坑），但将来要加「AI 先反问、用户再补图」这类多轮时，必须重新检查这一点
- **不设 `detail` 字段**：`low`（512×512）会把字压糊，而 `auto` 等价于原图。我们的分段尺寸已经在客户端调到了上游的最优像素预算（§5.1），没有可省的余地

### 4.4 名字解析（食材 / 单位 / 分类 / 标签）

统一顺序（沿用主规格 §4.3 的形状）：**精确匹配**（trim 后相等）→ **包含匹配**（唯一命中才认）→ **多命中给候选** → **零命中标记为未落定**。

| 字段 | 命中 | 未落定时的处理 |
| --- | --- | --- |
| **食材** | 直接填进表单该行 | **带进编辑页，保持「未选中」状态**，该行显示 AI 给的原始名字 + 一个待选标记，用户点它从候选里挑或新建（复用现有 `IngredientSheet`）。**不许静默新建**——库里会立刻多出「五花肉」「五花肉片」「五 花 肉」，而 AGENTS.md 的食材归一正是要防这个 |
| **单位** | 直接填 | **退化为 `unit_id = null`，数字保留**。单位表比食材表规范得多（克 / 毫升 / 个 / 勺），未命中说明图里写的是怪单位，用户在编辑页看到「2」而没有单位会自己补 |
| **分类** | 直接填 | **留空**，用户在编辑页选（现有校验要求非空，保存时自然会拦住） |
| **标签** | 直接填 | **不给模型猜的机会**——标签由模型**从 prompt 里给的库里已有标签中选**，选不出来就是不给。这样不会出现"库里没有的标签"这种状态 |
| **「适量」「少许」** | —— | `amount = null`、`unit_id = null`。**不是 0，不是把「适量」当单位名** |

保存前的一项新增校验：**每一行食材都必须有 `ingredient_id`**（未落定的行会拦住保存）。这是本设计在 `RecipeEdit` 上唯一新增的交互状态。

### 4.5 本地会话与图片存储

新增两张本地表（**必须同步改 `migrateTables`，且必须用测试钉住它们不进同步**）：

```sql
ai_sessions(id, created_at, updated_at, deleted_at)
ai_messages(id, session_id, role, content, payload, prompt_version, created_at, updated_at, deleted_at)
```

- 按 AGENTS.md 的硬约束，两张表都带 `id / updated_at / deleted_at`；但**永不参与同步**，理由同主规格 §10.5（对话含用户的厨房情况与截图，没有任何理由把它送上服务器）
- `payload` 是 TEXT(JSON)：截图轮的图片以 dataUrl 存这里，`content` 仍是纯文本（M4 §4.1 的形状，含 `mime / dataUrl / width / height / bytes`）
- **图片只在本机 SQLite，绝不进同步**；客户端离线时选中/接收的图**不落库**（发不出去就不留）
- `prompt_version` 随会话落库（主规格 §7.1 同款），将来改 prompt 后老会话行为可追溯

## 5. 客户端架构

目录与 wee-count 同构（已在那里验证过依赖方向，不重新设计）：

```
src/services/ai/
  prompt.ts      system prompt 组装 + PROMPT_VERSION
  filter.ts      工具参数校验（手写，不引 zod）+ 名字解析 + 组 RecipeFilter
  transport.ts   调 /api/v1/ai/chat，把 ApiResult 映射成正常值/异常
  agent.ts       编排循环、工具分发、错误映射
  session.ts     会话落库/读回 + 历史替换
  image.ts       选图 + 读字节 + 压缩（plugin-dialog / plugin-fs 在此收口）
  longImage.ts   纯函数：分段切割 + 封面裁切矩形（无 DOM 依赖，可直测）
src/stores/aiChat.ts
src/components/ai/{ChatBubble,ChatComposer,AttachmentPreview}.vue
```

- `AiPage.vue` 从占位改成聊天页，路由不变
- 检索结果卡片**复用现有 `RecipeCard.vue`**，点击进 `/recipe/:id`
- 结果旁给一个「在筛选页继续改」的入口：把解析后的 `RecipeFilter` `apply()` 进 `recipeFilter` store 再跳 `/` ——**与手点漏斗图标走完全同一条路径**，这是「AI 的结果你能自己验」的核心机制
- 截图轮结束时 `router.push("/recipe/new")`，`RecipeEdit` 挂载时**消费一次**草稿槽（读走即清，切页回来不再重复预填）
- **封面**：分段之前，用同一个 canvas 把长截图第一屏裁成宽 `MAX_WIDTH`、高不超过 `MAX_WIDTH × 4/3` 的普通比例图，**在跳转之前**写进 `imageStore`，路径随草稿槽一起带过去填 `cover_path`。裁切或写盘失败 ⇒ 封面留空、**不阻断跳转**（用户可在编辑页自己选图）
- 草稿槽被消费后若用户没保存，那张封面文件就是孤儿 —— 与 `ImagePicker` 的既有行为一致（选了图不保存本来就留孤儿），本设计**不新增清理机制**
- 输入区底部固定 + `useKeyboardInset()`（安卓键盘顶掉输入框是必踩的坑）

### 5.1 `longImage.ts` 分段算法

- 目标：把长图按**宽度**缩放到 `MAX_WIDTH = 1080`，纵向每段不超过 `MAX_SEGMENT_HEIGHT = 1500`（**含**与相邻段重叠的 120px），**相邻段之间重叠约 120px**（避免一行字被切在段边界上，模型两段都能看到它）
- **这两个常量不是拍的**：上游会把每张图按「总像素数归一到约 1300×1300」二次缩放（DeepSeek vision 指南「Token Usage」节）。
  1080 × 1500 ≈ 1.62M px < 1.69M px ⇒ **我们的段送上去不再被缩小**，字不会被二次压糊。
  段再高就会开始糊：1080 × 3000 会被缩到约 780 × 2160，正是要避的事
- 每张图在上游封顶 **1024 token**（同上节），与像素尺寸无关 ⇒ 6 段最多约 6k 视觉 token，成本可控（§11.4）
- 每段单独 JPEG 编码（质量起点 0.8）
- 纯函数只负责算切割矩形（输入：原始宽高，输出：`{x,y,w,h}[]`），编码在 `image.ts` 里做 —— 这样切割逻辑可以脱离 canvas 直测
- 极端情况必须处理：宽高为 0 / 1px、纵横比 < 1（横图不该被分段）、段落数为 1 时不分段
- **段数上限 6**。超过则拒绝并提示「这张图太长了，截短一点再发」——不做无限分段，一次调用塞十几张图既贵又容易触发上游限制

## 6. 后端 `/api/v1/ai/*`

**整体沿用主规格 §6 与入口规格**：`POST /ai/chat`、`GET /ai/status`；配置项同名同默认值；`AI_API_KEY` 不进必填校验；
限流按 userID、分钟级在外层日配额在内层、`/ai/status` 不吃日配额；日志只记 `user_id` / 耗时 / tokens / `finish_reason`，
**不记消息内容**；错误映射表照抄主规格 §6.6。

只列差异：

| 项 | 值 | 理由 |
| --- | --- | --- |
| `maxAIBodyBytes` | **12 MiB**（主规格是 256KB，M4 提到 4MiB） | 算术见下：1 MiB 原始字节 base64 后 ≈1.33 MiB，6 段 ≈ 8.0 MiB，再加历史与 tools schema。**定 8 MiB 会让合法的 6 段输入直接 413** —— 下面三个常量必须一起算平 |
| 单段压缩后上限 | **1 MiB**（与 M4 同，是上限不是目标值） | 1080×1400 的 JPEG q0.8 通常只有 200–400 KB，1 MiB 是兜底 |
| 一次请求的段数上限 | **6**（客户端与后端共识常量） | 6 × 1.33 ≈ 8.0 MiB < 12 MiB，留出余量 |
| 上游超时 `AI_TIMEOUT` | **120s**（主规格默认 60s） | 多块长图的视觉推理比一张小票慢得多 |
| AI handler 的读写超时 | 用 `http.NewResponseController(w)` 在**该 handler 内**解除 `ReadDeadline` / `WriteDeadline` | 全局 `ReadTimeout: 15s` / `WriteTimeout: 60s` 会掐断 120s 的上游等待，也会掐断移动网络下的 8 MiB 上传。**不动全局值**——那是给所有路由的，为 AI 放宽等于给全部端点放宽 |
| 模型配置 | **一个键**：`AI_MODEL`，默认 **`deepseek-flash`** | `deepseek-flash`（V4.1-Flash）**同时支持视觉与工具调用**，一条链路一个模型就够。⚠️ 不要照抄主规格的默认 `deepseek-chat`——它**不接受 `image_url` 内容块**，截图这条路会开箱即 400（单测钉住，§9.16） |
| 上游硬限制（供常量校验） | body 48 MiB；单图 32 MiB；单边 ≤8192 px；每条消息 ≤600 图；图片仅限 `user` 消息 | 我们自己的 12 MiB / 1 MiB / 1080px / 6 段全部宽松落在这几条之内，没有一条会先撞上游 |

`GET /ai/status` **沿用入口规格的 `{ enabled, model, host }`，不加 `vision_enabled`**：只有一个模型键，客户端无从判断它支不支持视觉，
而做能力探测要多一次请求。模型不支持时就走 §8 里上游 400 那条文案路径（M4 §8 同款），不在客户端预判。

后端**零 schema 变更、零 migration、不碰同步协议、不读一行菜谱数据**（末一条是上面说过的自我约束）。

## 7. System Prompt 与隐私

### 7.1 prompt 组成

每轮都带：

```
1. 角色与硬约束（不编造、不声称已保存、不调不存在的工具、不输出 id）
2. 今天日期
3. 库里已有的分类全量 + 标签全量（只给名字）
4. 工具说明 + few-shot
5. 输出约定
```

**不给食材全量、不给单位全量。** 这是与主规格 §7.1 的**有意偏离**，理由是一条实打实的成本：

- 记账的字典（分类 / 账户 / 标签）是用户手工维护的，几十条封顶
- 食材表是**用户自己长出来的**，几百条起步，且可能上千 ⇒ 塞进 prompt 会让每一轮都带上 1–3k tokens，且随库增长
- 而模型**根本不需要知道食材字典**：检索时它只需说用户说的那个名字（本地解析），识别时它只需读出图里写的名字（本地解析）。字典在本地，不在 prompt 里
- 分类和标签必须给，是因为**识别场景下模型要"从库里选一个"**——它猜一个不存在的分类名，等于白猜

few-shot 至少四条：`找有五花肉的菜` → `search_recipes`；`今晚想吃辣的下饭的` → `search_recipes`（多个条件）；
`（长截图）` → `create_recipe_draft`；`我库里有哪些分类` → **直接答不调工具**。

**能力缺口，prompt 里必须明说**：筛选对象只有关键词 / 分类 / 标签 / 食材四维，菜谱表里**没有时长、难度、几人份**字段
⇒ 「半小时能做完的」「简单的」「三人份的」这类条件**筛不了**。模型必须直说做不到，不许悄悄丢掉条件、拿四维里最接近的糊弄过去
（丢条件比做不到更糟：用户以为筛过了）。

**禁止清单**（每条对应一个真实事故）：不得编造菜谱；**不得声称已收录**；不得调用不存在的工具；不得输出 id；
不够确定就直接说看不出，不要拼一个像样的菜谱出来。

### 7.2 检索范围：只有本地库

`search_recipes` 跑在 `filterRecipes()` 上（§4.1），命中的是**当前账号可见的本机菜谱**（含自己账号同步下来的）。

社区菜谱（`/community/recipes` 走的 REST）**不进检索**：它们不在本地 `recipes` 里，把 AI 检索拆成「本地 + 一次远端分页拉取」会让
「matched 说 3 道、点进去 5 条」这类对不上的崩坏成为常态——正是主规格 §4.6 要避免的信任崩塌。搜索结果为空时的正确引导是「去逛社区」，由界面给，不给模型。

### 7.3 隐私

- **发给上游的**：用户输入原文；system prompt（分类名与标签名）；**整张截图**；检索命中的菜谱**名称、分类名、标签名、食材名**
- **绝不发的**：菜谱步骤正文以外的内容其实都在上面了——但**用量与步骤文本只在截图轮的识别结果里往返**，检索轮不发；不发账户信息、不发服务器地址、不发任何凭据
- **两层开关**（沿用主规格 §7.3）：后端 `AI_API_KEY` 为空 = 能力层关闭；客户端「我的 → 隐私」独立开关，**默认关闭**，开启前必须先看说明卡。
  这个开关区块在 `MePage.vue` 里是**净新增**（§2），落盘走 `settingsFile.ts`（与服务器地址同一层），**不另开存储**
- 首次说明卡文案要点：「启用后，你的提问、分类与标签名称、命中的菜谱名称与食材会发送到 `<host>`。**你发出的截图会整张发给它，可能包含你的账号昵称、点赞数等页面上的其他信息。** 可随时在「我的 → 隐私」关闭。」
- `<host>` 取自 `/ai/status`，**拿不到 `host` 不得展示说明卡、不得允许开启开关**（入口规格同款）
- 关闭开关**不删历史**，但停止发送
- 聊天记录与截图**明文落盘**，说明卡里要讲清楚（同主规格 §7.3）
- `/ai` tab 的显隐按**入口规格 §5 的三态**来，不是「探不到就藏」：
  - opt-in 开关**关着** ⇒ 隐藏（用户没同意，入口不该在）
  - 开着且服务端**明确回 `enabled:false`** ⇒ 隐藏
  - 开着但**探活失败 / 还没探**（未配服务器地址、断网、未登录）⇒ **不隐藏**，页面上说清「需要先连接服务器」
  理由：把「探不到」当成「没启用」，一次断网就会永久藏掉入口，而用户没有任何办法找回来

## 8. 失败路径与文案

| 情形 | 行为 | 用户可见文案 |
| --- | --- | --- |
| 未配服务器地址 | `/ai` tab 隐藏 | —— |
| 后端没配 `AI_API_KEY` | `/ai` tab 隐藏（`/ai/status` 报 disabled） | —— |
| 隐私开关未开 | 聊天页显示说明卡，输入区禁用 | —— |
| 截图段数 > 6 | 拒绝，不进入输入区 | 这张图太长了，截短一点再发 |
| 单段压缩后 > 1 MiB | 拒绝 | 图片太大，换一张或先裁剪 |
| 选中的不是图片 | 拒绝（按魔数判定，不按扩展名；上游也是按内容判类型，M4 §9.7） | 只支持 JPEG / PNG / WebP / GIF 图片 |
| 选中了动图（GIF） | **接受，只取首帧** | 客户端本来就要用 canvas 重编码为 JPEG，首帧是自然结果；为此写一条拒绝分支反而是多余的代码 |
| 上游 400 且这轮带图 | 按 M2 映射（判在 `agent.ts`） | 这条没发出去：可能是当前模型不支持图片 |
| 模型看不出这是菜谱 | 正常回答，**不跳转编辑页** | 由模型说明 |
| 识别出的菜谱有未落定食材 | 跳转编辑页，未落定行拦住保存 | 这几样食材没对上，点一下选一个 |
| 取消 / 超时 / 429 / 日配额 | 沿用主规格 §6.6 | 沿用 |
| 搜索无结果 | 不跳转，卡片区给空态 | 库里没找到，去社区逛逛？ |

## 9. 测试策略

**客户端纯函数（vitest）**

1. `longImage` 分段：小于上限不分段；按宽度缩放不按最大边；极端纵横比（1:20）不出现 0 边；重叠区正确；段数上限 6 触发拒绝；封面裁切矩形落在第一屏内；**单段像素数 ≤ 1300×1300（上游二次缩放的阈值，这条是 `MAX_WIDTH` / `MAX_SEGMENT_HEIGHT` 的看门测试）**
2. 名字解析：精确命中 / 唯一包含命中 / 多命中给候选 / 零命中标记；trim 与全角空格
3. 「适量」⇒ `amount=null, unit_id=null`（**断言不是 0**）
4. 工具参数校验：非法 `categories` 类型、空对象、多余字段，各有错误码
5. 组装：带图轮 `content` 是多块 `image_url`（最后一块 `text` 可有可无）；无图轮是字符串；**无 `text` 时不出现空 `text` 块**
6. 历史替换：截图轮在上下文里变成占位符，本地存储与页面渲染**未被替换**
7. `RecipeEdit` 预填：草稿槽写完 → 挂载 → 表单被填 → **槽被清空**（再来一次不重复预填）
8. 未落定食材拦住保存
9. 「在筛选页继续改」：`apply()` 后的 store 内容与工具返回的 `applied` 一致
10. **AI 会话与消息表不进同步**（显式断言同步的逐表列举里没有这两张表）

**后端（Go）**

11. 键集哨兵：`role`+`tool_calls` 的消息到上游时**不得多出 `content` 键**（M4 §9.1 同款）
12. 字符串 `content` 与块数组 `content` 都原样透传（不解析、不重排）
13. 超过 `maxAIBodyBytes` ⇒ **413**（不是 400）
14. 限流中间件顺序：分钟级在外、日配额在内；`/ai/status` 不吃日配额
15. `AI_API_KEY` 为空 ⇒ `/ai/chat` 返回 **503** `ai_disabled`
16. 默认 `AI_MODEL` 是 `deepseek-flash`（钉住常量，防止退回 `deepseek-chat` 把截图路径打死）
17. 合法的 6 段请求体（≈8 MiB）**不触发** 413 —— 这是 §6 三个体积常量算平的看门测试

**不测**：Android 分享目标的真机行为、上游模型的识别质量。

## 11. 风险与未决项

1. **Android 分享目标只在真机暴露**（intent-filter 接 `image/*`，小红书长截图是 PNG）。`src-tauri/gen/android/.../MainActivity.kt` 与 `AndroidManifest.xml` 都在，条件具备；但改动**本环境验不了**，真机验收留到发布前。
   缓解：**整段移植分享目标规格**（§3）——那份已经把冷 / 热启动、`pending.json` 的 compare-and-delete、与会话自动锁的交叉逐个钉死
2. **长图里图与字混排**：小红书长截图会带上点赞数、作者名、「展开」按钮、水印。模型可能把「1.2万赞」当成食材用量。缓解：prompt 禁止清单里点明、编辑页让用户改；**不指望模型自己分辨干净**
3. **中文小字识别率**：按宽度缩放到 1080 后，小红书的正文字号约 14–16px 渲染，模型能不能读准是实测问题。
   `MAX_WIDTH` / `MAX_SEGMENT_HEIGHT` 现在有上游像素预算作依据（§5.1），**不是可随便调的旋钮**（调了必须同步改 §9.1 那条看门测试）；
   真正待实测的只剩**重叠像素**（起点值 120），它只影响片段边界处的字会不会丢一半
4. **token 成本（实测口径，风险比预想小）**：上游按尺寸归一，**每张图封顶 1024 token**（vision 指南「Token Usage」）
   ⇒ 6 段最多约 6k 视觉 token；Flash 档 cache-miss 输入 $0.15–0.30 / 1M tokens ⇒ 一次收录约几分钱。
   真正的成本风险在**段数失控**上，所以 6 段是硬闸，不是建议值
5. **跨段拼接**：做法步骤可能被切在段边界上。重叠 120px 是缓解不是解决；模型输出重复步骤时客户端不自动去重（去重规则比重复本身更容易出错），留给用户在编辑页删
6. **`RecipeEdit` 新增了「未落定食材行」这一状态**，是本次唯一动到现有录入页的地方。改动要小：该行 `ingredient_id` 为空 + 一个标记，保存前校验拦住
7. **识别出的菜谱没有步骤图**：小红书步骤图不提取（§4.2）。用户可能需要手工补图，价值略有折扣——但比手工录字省得多
8. **默认模型写错 = 功能不存在**：默认必须是 `deepseek-flash`。照抄主规格的 `deepseek-chat` ⇒ 截图这条路开箱 400。
   `.env.example` / `SELF-HOSTING.md` / `config.go` 三处默认值必须一致，并用单测钉住（§9.16）。
   **另**：wee-count 那边的默认值仍是 `deepseek-chat`，而官方定价页现在只列 `deepseek-flash` 与 `deepseek-v4-pro`——
   那个默认值可能已经失效。值得回那边单独核一次，**本设计不改别的项目的文件**
9. **检索能力有天花板**：菜谱表没有时长 / 难度 / 人数，所以「半小时能做的」这类条件天然筛不了（§7.1）。用户第一次这么问会觉得 AI 笨；由模型直说做不到，比悄悄丢条件好
10. **收藏来的社区菜谱搜不到**：自己截图收进来的菜谱能搜到，社区里收藏别人的**不在本地 `recipes` 里**，AI 搜不到（§7.2）。这是有意划的边界，界面上用「去逛社区」补上
